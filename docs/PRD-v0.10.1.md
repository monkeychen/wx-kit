# wx-kit v0.10.1 产品需求文档（迭代 PRD）

> **状态：需求已确认，待实施（2026-08-29）**。本版只解决 v0.10.0 的订阅可靠性、批量交付与可感知性能问题；验收以本文第 6 节为准。

## 1. 一句话定义

**订阅要只报一次，批量处理要一键完成，等待要看得明白。**

v0.10.0 在微信读书列表接口被服务端封禁后，保留 `/api/mp/cover` 的“每号最新一篇”增量订阅。
本版不改变该能力边界，而是让这条降级链路的身份判重、待处理批量下载和过程反馈符合用户预期。

## 2. 已确认事实与根因

### 2.1 `cover` 没有发布时间，不能用时间水位作身份

`/api/mp/cover` 返回稳定的 `reviewId`、标题和原文短链，但不返回文章发布时间。当前实现把每次读取
到的同一篇 cover 赋成“此刻”的 `createTime`；检查成功后又把这个值写入 `watermark`。下一次检查时，
同一篇会拥有更晚的伪时间，必然再次被判为新文章。下载层随后用文库判重返回“已存在”。

此前为解决“新订阅首次检查没有新文章”而把初始水位改为“最新时间 - 1 秒”，只让首次投递成立，
不能解决上述身份模型错误，也不应继续作为 `cover` 模式的判重手段。

### 2.2 列表探测已无产品价值

`/web/mp/articles` 已由三轮 spike 确认是服务端按账号+端点封禁。订阅检查仍先试该接口、失败后才读取
`/api/mp/cover`，会无意义地增加一次受保护网络请求与等待；不得把它当作将来可能自动恢复的探测。

### 2.3 下载慢有真实边界，也有可消除的体感损耗

微信请求治理要求跨账号串行，并对微信读书请求保留 2.5–5 秒间隔；正文、图片与视频下载也需受同一
网关保护，不能为提速改成并发轰击。当前可优化的是：移除无效列表探测、修复重复下载入口、并让用户
看见正在下载正文/图片/视频/导出的哪个阶段。

## 3. 需求清单

### R1 · `cover` 稳定身份游标，消除重复新文章

**用户目标**：刚订阅后，当前最新文章可被发现一次；已经检查、下载或忽略过的同一篇不应再次提示；
作者发布另一篇时才提示更新。

**方案**：

- 在订阅账号中新增 `latestArticleId`（实际存 `reviewId`；旧数据缺省视为未建立游标），与历史列表的
  `watermark` 分离。`watermark` 保留给旧数据兼容及未来真正能取得发布时间的列表来源。
- `cover` 探测返回稳定身份与展示信息；核心检查按身份比较，而非虚构 `createTime`。
- 首次成功读取 cover：没有游标则投递当前文章一次；成功检查后立即持久化该身份，无论策略是仅提示、
  自动下载还是用户随后忽略。下载失败仍作为 `newRefs` 待处理，不靠重复检查重建。
- 升级旧订阅时，若当前 cover 已在待处理列表或本地文库/下载历史中，建立游标但不再提示；否则按首次
  订阅投递一次，避免静默吞掉真实未处理的最新文章。
- 订阅检查直接请求 `/api/mp/cover`，删除生产链路中的 `/web/mp/articles` 试探；旧列表实现可保留为
  非生产历史代码，不再由订阅检查调用。

### R2 · 下载全部待处理新文章

**用户目标**：点击“检查全部”后，多个公众号均有新文章时，可以一次性下载，不必逐行操作。

**方案**：

- 当订阅页存在待处理文章时，显示唯一全局动作：`下载全部待处理新文章（N 篇，M 个公众号）`。
- 操作对象是所有已订阅账号当前的 `newRefs`，包括此前检查留下的失败待重试项；不另造账号级复选框。
- 保留现有行内展开和文章级勾选，供用户处理部分文章；全局按钮不与它争夺选择状态。
- 全局批量仍按既有全局网关串行执行；成功、已存在和不可访问文章从待处理移除，真实故障保留以便重试。
- GUI 与 CLI 本版不新增新的批量下载命令。CLI 用户仍可用既有 `subscription check-now` 的自动下载策略；
  本需求解决的是订阅页“检查后集中处理”的 GUI 缺口。

### R3 · 减少无效等待并展示真实进度

**用户目标**：用户能区分“系统在安全等待”“正在抓正文”“正在下载图片/视频”“正在导出”，而非只看到
长时间的“下载中 0/1”。

**方案**：

- 移除 R1 中的列表探测，减少每个账号至少一次无效请求与相应间隔等待。
- 将下载进度事件扩展为用户可读阶段，至少覆盖：等待微信请求窗口、获取正文、下载图片、下载视频、
  生成文件、完成/失败；图片和视频显示当前项/总项。
- 不缩短请求保护间隔、不并发下载文章、不改变视频按体量设超时的策略。速度上限受外部网络和风控约束，
  本版承诺消除无效工作与盲等，不承诺固定秒数。

## 4. 交互约定

- “检查全部”结束后：有待处理文章则页面顶部显示全局下载按钮；没有待处理文章则不占空间。
- 批量下载期间：显示总计 `已完成/总数`、当前公众号和阶段；行内下载与检查全部按钮禁用，避免和全局
  串行任务竞争。
- 单号行仍可展开、选择、下载或忽略；全局下载不会修改用户在展开面板中的勾选状态。
- 首检、无新文章、重复文章、下载失败在话术上必须区分；不再把“文库已有”伪装成“发现新文章”。

## 5. 非目标

- 不恢复按公众号批量下载历史、`crawl` 或微信读书列表接口。
- 不增加账号级多选、下载队列并发度、自动重试或多账号池。
- 不承诺微信读书或公众号资源的固定下载时长。
- 不迁移或删除旧订阅/文库数据；新增字段须向后兼容旧 `subscriptions.json`。

## 6. 验收清单（逐条）

- [ ] 新订阅账号首次检查发现当前最新文章一次；下载后立即再检查，显示无新文章且不触发下载。
- [ ] 同一篇在“仅提示”“自动下载”“忽略”“下载失败后重试”各路径下均不因再次检查重复入待处理。
- [ ] `cover` 模式订阅检查不访问 `/web/mp/articles`；离线测试能证明只构造 `/api/mp/cover` 请求。
- [ ] v0.10.0 旧订阅数据升级后，当前文章若已在待处理或已在库中，不重复提示；未知旧状态不静默漏掉最新文章。
- [ ] “检查全部”后有多个账号待处理时，出现“下载全部待处理新文章（N 篇，M 个公众号）”；完成后各行和总数同步刷新。
- [ ] 全局下载仅移除成功、已存在或不可访问项；真实失败项保留并能再次下载。
- [ ] 下载中显示当前公众号及正文/图片/视频/导出阶段；不放宽请求保护间隔、不引入文章并发。
- [ ] `npm test`、`npm run lint`、`npx tsc --noEmit -p tsconfig.json`、`npm run build`、当前有效 GUI e2e 全绿；真实文章 URL 下载与真实 `cover` 增量检查单独报告，不以 fixture 替代。
