# M35 实现计划 — 含视频文章下载(v0.8.2 R2)

> 对应 `docs/PRD-v0.8.2.md` R2。分支 `feat/m35`。
> **收集需求时对这条的理解有两处偏差,实现前抓真实页面纠正了**(见下)。范围比原以为的大:
> 不只是「多下一个 mp4」,而是**视频消息页当前的下载产物是坏的**——这是个未被发现的 bug。

## 已核实的事实(2026-07-26 抓真实页面实测,实现按这些来)

测试 URL `https://mp.weixin.qq.com/s/bXUTSRQ_zIvyigWiqw3UfA`(2.4MB HTML)。

### 1. 它不是「正文嵌了视频的图文」,是**视频消息页**

`window.appmsg_type = '10002'`、`item_show_type: '5'`;页面结构是
`rich_media_area_primary video_channel` → `js_video_channel_container` → `<div id="js_mpvedio" class="mpvideo_wrp"></div>`(**空 div,播放器由前端 JS 渲染**)。
**页面里没有 `rich_media_content`** —— 这类页面没有富文本正文,内容 = 标题 + 描述文字 + 视频。

### 2. 现状是**坏的**:下下来是 21 万字符的内联 JavaScript

跑现有 `parseArticle` 实测:title/account/author/publishTime/digest/coverUrl 全对,但
`imageUrls: 0`、**`contentHtml` 长 218510 字符,内容是 `share_notice` 壳 + 大段内联 `<script>`**。

**根因**:`#js_content` 在视频页里**存在但是错的容器**——它是分享提示壳
(`<div id="js_content" class="share_notice_wrp">`,在 `#video_share_global_info` 里)。
于是 `parse-article.ts:139` 的分流条件 `if (!contentHtml.trim())` **不成立**,
M19 建立的「非标准消息类型走脚本变量」通道被跳过,那个壳被直接当正文返回。
→ **正文修复与「下不下视频」无关,是无条件的 bug 修**。

### 3. 视频信息结构(`video_page_info`)

```
video_page_info: {
  video_id: 'wxv_4601001312020021250',
  mp_video_trans_info: [ { format_id, width, height, duration, filesize, url,
                           video_quality_level, video_quality_wording }, ... ]
}
```

### 4. **`format_id` 与清晰度无关 —— PRD 里的排序假设是错的**

实测四档:

| format_id | 分辨率 | 体积 | quality_level | wording |
|---|---|---|---|---|
| **f10002** | **1572×1080** | **133.5 MB** | 3 | 超清 |
| f10102 | 1080×740 | 39.5 MB | 3 | 超清 |
| f10004 | 698×480 | 37.6 MB | 1 | 流畅 |
| f10104 | 480×328 | 12.9 MB | 1 | 流畅 |

PRD 收集阶段写的 `f10104 > f10102 > f10004 > f10002` **完全反了**(f10104 是最小的那档)。
**择清晰度必须按 `width × height`**(filesize 做 tie-break),**绝不能按 format_id 数值猜**。
`video_quality_wording` 只有「超清/流畅」两档且重复,不足以排序。

### 5. 直链的转义与时效

URL 在脚本里的形态:`...mp4?dis_k=...\x26amp;dis_t=1785044618\x26amp;auth_key=...`
—— **`\x26amp;` 要解成 `&`**(先 `unescapeJsString` 把 `\x26` 解成 `&`,再把 `&amp;` 解成 `&`;
M19 的 `extractPictureMessage` 已有同样的 `.replace(/&amp;/g, '&')` 先例,照抄)。
`dis_t` 是签发时间戳、`auth_key` 是签名 → **有时效,必须本次流程内下完,URL 绝不入库**。

### 6. 正文文字在 `content_noencode`(M19 已用过的同一字段)

`desc` 与 `content_noencode` 内容相同(本例 280 字,与 og:description 一致)。
M19 的 `extractPictureMessage` 已在读 `content_noencode`,**提取正则可复用**。

### 7. 封面

`video_page_info` 附近有 `cover_url` / `cdn_url`(mmbiz.qpic.cn jpg),与 `og:image` 同源。
封面走既有 `cover` 格式即可,**不必新做**。

### 8. 体积印证了「video 不进默认格式」

最高清 **133.5MB**。默认下会拖垮批量抓取,且用户毫无预期。
→ 保持 PRD 决策:`video` 是显式格式;**下载必须有进度**(否则看着像卡死)。

## 步骤(bite-sized,TDD,每步跑 `npm test`)

### A · fixture(照 M19 惯例:真实页裁成小样本)

- **A1** 从真实页面裁出 `tests/fixtures/video-message.html`(目标 <15KB,对齐 `picture-message.html` 的规模),

  `window.appmsg_type = '10002'`、**装着 script 的 `#js_content` 分享提示壳**(否则测不到 bug)、
  完整四档 `mp_video_trans_info`(URL 的 `\x26amp;` 转义保持原样)、`content_noencode`。

### B · 视频源提取(`src/core/parse-video.ts`,纯逻辑)

- **B1(红)** `tests/core/parse-video.test.ts`:
  - `extractMpVideos(fixtureHtml)` 返回 1 个视频,`videoId === 'wxv_4601001312020021250'`。
  - **择档 = 最高像素**:`width===1572 && height===1080`,`formatId==='10002'`(**钉死「不是按 format_id 最大」**)。
  - `url` 已解码:含 `&dis_t=`、`&auth_key=`,**不含 `\x26` 与 `&amp;`**。
  - `filesize === 139984916`、`durationMs`/`duration` 取到。
  - 无 `video_page_info` 的普通图文页 → 返回 `[]`。
  - 只有 `mp_video_trans_info: []`(空数组)→ 返回 `[]`(有 video_page_info 但无可下档位)。
- **B2(绿)** 实现:
  ```ts
  export interface MpVideoSource {
    videoId: string; formatId: string; url: string
    width: number; height: number; filesize: number; durationMs: number
    qualityWording: string
  }
  export function extractMpVideos(html: string): MpVideoSource[]
  ```
  截取 `video_page_info:` 到其 `mp_video_trans_info` 段再逐项匹配(**先截段**,同 M19 的教训:
  整页匹配会撞上别处同名字段);择档 `sort((a,b) => b.width*b.height - a.width*a.height || b.filesize - a.filesize)[0]`。

### C · 视频页正文修复(无条件 bug 修,与格式无关)

- **C1(红)** `tests/core/parse-article.test.ts` 加 describe「视频消息(appmsg_type 10002)」:

  - `videos.length === 1`(ParsedArticle 新字段)。

  - **分流提前**:视频消息时**不信 `#js_content`**,直接走 `content_noencode` → `textToParagraphs`;
    正文为空也可接受(有些视频没描述),此时 contentHtml 为空串而非脚本垃圾。

## 后续修正(2026-07-26,安哥试用 `npm run dev` 后反馈)

**反馈一:不该有「视频」这个格式选项。**
> 「本来这个下载选项是说,下载的内容要包括所选中的类型,你直接加了个『视频』选项,
> 如果我提供的链接是一普通文章呢?我的理解是,如果提供的链接包含视频,那你就把视频下载下来就行。」

**安哥是对的,这里把「内容」错当成了「格式」**:
`cover/md/html/pdf/meta` 是同一份内容的不同**表现形式**;视频是**内容本身**。
图片从来没有「图片」选项——图片是内容,自动本地化。视频与图片同类,只是大。
链接是普通文章时,那个选项什么都不会发生,纯属噪音。

改法:
- `DownloadFormat` 移除 `'video'`,`FORMAT_INFOS` 移除「视频」项 → **有视频就下,不需要选**。
- 体积保护改由设置项 `downloadVideos`(默认 **开**)承担;CLI 给 `--no-video`。
  理由:按公众号抓 200 篇可能撞上多个视频消息,单个上百 MB,批量前得有地方关掉——
  但默认路径必须无感(安哥定:「设置里留个开关,默认开」)。
- 订阅检查的自动下载按设置走(没有 flag 可依赖)。

**反馈二:md 视图里点视频链接会退回下载页。**
根因:`Reader.tsx` 的 `ReactMarkdown components` 只覆盖了 `img`,没覆盖 `a`,
于是 `[📹 视频](videos/video-1.mp4)` 是个普通相对链接,点击把 hash 路由带偏,被路由兜底扔回默认页。
改法:**与 `img` 同构**——指向 `videos/` 的链接直接渲染成 `<video controls>`(md 里的
`![](images/…)` 本就渲染成 `<img>`)。这样连「点」都不需要,bug 从根上消失。
顺带把站外 `http(s)` 链接改为 `openExternal`——同一个坑的另一半(应用内导航过去就出不来了)。
