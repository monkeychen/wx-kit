# M39 实现计划 — 更新检查在「常开的应用」里也要生效(v0.8.4 R1)

> 对应 `docs/PRD-v0.8.4.md` R1。分支 `feat/m39`。
> 改动很小,但**放错层就白改**:限流与缓存的决策必须落在可单测的 core,
> 定时 tick 必须落在主进程(渲染层的 timer 在关窗后就没了)。

## 已核实的事实(2026-07-27 读代码 + 读真实 settings)

- 静默检查唯一的触发点在 **渲染层挂载后 3 秒**(`MainLayout.tsx:29-36`),
  **关窗驻留后这个 effect 不再跑**;桌面应用常年不重启 → 实际可能几天都不查一次。
- 限流写死在 `ipc.ts:344-348`:`silent` 且 24h 内有记录 → **`return null`**,
  请求没发、**上次的结论也没留**,渲染层拿到 `null` 只能当「没有新版」。
- `checkUpdate()` 任何失败都返回 `null`(设计如此,别改),**所以调用方无法区分
  「查了没新版」「被限流」「查失败」**——这正是 bug 的形状:三种情况长得一模一样。
- settings 里只有 `lastUpdateCheckAt`,**没有任何地方存过「上次查到了什么」**。
- `SubscriptionScheduler` 已有一套可抄的形状:主进程每分钟 tick + 防重入 + 失败不影响其余。
- 真实污染实录:`npm run dev` 与正式安装**共享真实 userData**,M37 验证期间的 dev 启动
  把 `lastUpdateCheckAt` 写成了 14:29,于是安哥 13:54 启动的那个进程注定查不到。
  (CLI 的 `update --check` **不写 settings**,不是污染源——本次实现也不给它加写入。)

## 设计决策(先定,免得实现时摇摆)

1. **缓存的是「上次查到的 release」,不是「上次的 hasUpdate」**。
   `hasUpdate` 必须**用当前版本重算**——升级后本地版本 ≥ 缓存版本,提示自动消失,无需清理逻辑。
2. **限流照旧,但被限流时返回缓存而不是 `null`**。限流的本意是省请求,不是隐瞒结论。
3. **静默检查失败时也回落到缓存**(断网不该让已知的新版提示消失);
   **手动检查失败仍返回 `null`**——手动是用户主动问「现在什么情况」,拿旧结论冒充成功是撒谎。
4. **tick 放主进程**(新 `UpdateScheduler`),关窗仍在跑;查到有新版**广播给渲染层**。
   渲染层挂载时那次 silent 调用保留(走缓存、零请求),负责「开窗即知」。
5. **tick 间隔 60 分钟,请求频率仍由「每天最多一次」兜底**——tick 变频繁 ≠ 请求变频繁。
6. **开关关掉时:既不请求、也不用缓存提示**。用户关掉的是「别拿这事烦我」,不是「别发请求」。

## 步骤(bite-sized,TDD,每步跑 `npm test`)

### A · 决策逻辑进 core(`src/core/update-gate.ts`,新文件)

- **A1(红)** `tests/core/update-gate.test.ts`:
  ```ts
  decideUpdateCheck({ silent, enabled, lastCheckedAt, now }) // → 'check' | 'cache' | 'skip'
  ```
  - 手动(`silent: false`)→ 永远 `'check'`(即使关了开关、即使刚查过)。
  - 静默 + 关开关 → `'skip'`。
  - 静默 + 开 + 24h 内查过 → `'cache'`(**不是 skip**,这是本次修复的核心)。
  - 静默 + 开 + 从未查过 / 超 24h → `'check'`。
  - 边界:恰好 24h 算超时(`>=`)。
- **A2(红)** `infoFromCache(cached, currentVersion)`:
  - 缓存版本 > 当前 → `hasUpdate: true`,字段(notes/publishedAt/assets)原样带出。
  - 缓存版本 ≤ 当前(已升级)→ `hasUpdate: false`,**不必删缓存**。
  - 无缓存 → `null`。
- **A3(绿)** 实现。类型 `CachedRelease = Omit<UpdateInfo, 'current' | 'hasUpdate'>`
  ——**从 UpdateInfo 派生,不另写一份字段**(两份必漂)。

### B · settings 落缓存(`electron/services/settings.ts`)

- **B1** `AppSettings` 增 `lastKnownRelease: CachedRelease | null`(默认 `null`),
  注释写明「存的是上次查到的 release;`hasUpdate` 按当前版本实时算,不存」。
- **B2** 不进 `settings-cli.ts` 的可设置白名单——**这是运行期状态,不是用户偏好**。
  (若该文件是显式白名单则无需改动,确认一下即可。)

### C · IPC 接上(`electron/ipc.ts`)

- **C1** 把 `update:check` 的处理体抽成一个可复用的 `runUpdateCheck(silent)`
  (scheduler 与 IPC 共用一份,**别在 scheduler 里再写一遍限流**)。
  ```
  decideUpdateCheck → 'skip'  → null
                    → 'cache' → infoFromCache(s.lastKnownRelease, version)
                    → 'check' → checkUpdate();
                                成功 → 存 lastUpdateCheckAt + lastKnownRelease,返回
                                失败 → silent ? infoFromCache(...) : null
  ```
- **C2** 成功查到时**总是**写 `lastKnownRelease`(哪怕 `hasUpdate: false`)——
  它是「上次查到的事实」,不是「待提示的通知」。

### D · 主进程定时 tick(`electron/services/update-scheduler.ts`,新文件)

- **D1** 抄 `SubscriptionScheduler` 的形状:`start()` 起 60 分钟 `setInterval`,
  防重入,`catch` 全吞(更新检查失败不该影响应用任何其它部分)。
  **不在 `start()` 里立即 tick**——启动那次由渲染层的 3 秒延迟负责,重复调用没意义。
- **D2** tick 拿到 `hasUpdate: true` → 向所有窗口 `webContents.send('update:available', info)`。
- **D3** `ipc.ts` 末尾与 `SubscriptionScheduler` 并列启动。

### E · 渲染层收广播(`MainLayout.tsx` / `preload.ts` / `api.ts`)

- **E1** `preload` 暴露 `onUpdateAvailable(cb)`(与既有 `onSubscriptionsUpdated` 同形,返回取消订阅函数)。
- **E2** `MainLayout` 订阅该事件 → 点亮小圆点。**挂载时那次 silent 调用保留**。
- **E3** 圆点的告知强度不变(不弹窗、不 toast)——M37 定的,别趁机加码。

## 验证(不可省)

- `npm test`、`npm run lint`、`npx tsc --noEmit`、`npm run test:e2e`。
- **复现原场景(必须真跑)**:用**隔离的 `--user-data-dir`**(教训见上)造出
  「`lastUpdateCheckAt` = 刚刚 + `lastKnownRelease` = 0.8.4 + 当前版本 0.8.3」的状态,
  启动 GUI → **圆点应亮**(走缓存,零请求)。这正是安哥那台机器的处境。
- 关掉「启动时检查更新」→ 同样状态下**圆点不亮、也不发请求**。
- 手动点「检查更新」→ 不受限流影响,真发请求(抓包或看 `lastUpdateCheckAt` 是否更新)。
- 断网(改 host 或断 Wi-Fi)→ 启动不卡、无错误弹窗;已有缓存时圆点仍亮。
