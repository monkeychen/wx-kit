# M44 实现计划 — 列表接口回退至 `cgi-bin/appmsg?type=9`

> 安哥 2026-08-02 决定。分支 `feat/m44`。**合 main 暂不发版**——等账号解封真机验证通过再走发版流程。

## 背景（为什么做这个）

换用 `appmsgpublish`（M36）后约一天，登录账号被微信频控（`ret=200013 freq control`），持续 24 小时不恢复。诊断（探针对比同 session 同 fakeid 打两个端点）证明：**两个端点同时 200013，是账号级频控，与端点无关**——所以换回 `appmsg` 当下并不能解封。

但安哥的决定有合理内核：`appmsgpublish` 每页 20 组、聚合群发、返回数据多，可能更耗频控配额、解封后更容易再触发；旧 `appmsg` 每页实回 ~5 条、更轻。权衡是：**牺牲文字/视频消息的列表覆盖，换更小的频控压力**。这是产品取舍，安哥拍板。

这是 M36（`23e5b0e`）的反向撤销，但**不是盲目 git revert**——M36 之后围绕 `appmsgpublish` 长出了去重主键透传、类型分发、不可见过滤等机制，其中多数与端点解耦、可以保住。本计划只换「端点 + 解析层」，下游机制尽量保留，`appmsg` 不提供的字段显式降级。

## 调研结论（Explore 已确认）

**能保住的（与端点解耦）：**
- **去重主键链**：`ArticleRef.appmsgid/itemidx` → `mp-crawl` → `download-queue` → `article-id.canonicalId`，整条链不变，只在 `fetchPage` 换读取的 JSON 键。`app_msg_list` 项通常带 `appmsgid`/`itemidx`；**即使缺**，旧接口给长链接（含 `mid`/`idx`），`articleId()`（`article-id.ts:23-25`）从 URL 解析兜底。去重不会崩。
- **解析阶段类型识别**：`parse-article.ts:139` 从文章 HTML 读 `itemShowType`，与端点无关。下载后的 `meta.json` 仍有真实类型。
- **不可见文章下载阶段兜底**：`ArticleUnavailableError`（`download-article.ts` / `download-queue.ts`）从下载时的 HTML 识别，与端点无关。移除列表侧预过滤后，审核失败/删除文章仍在下载时被认出。

**会丢失的（appmsg?type=9 的已知限制）：**
- **列表/digest 阶段文字消息(10)+视频消息(5)消失**：`type=9` 只回 `item_show_type=0` 的图文。v0.8.2 R4 实测过（370 vs 770 篇），安哥已接受。
- **列表阶段类型标注失效**：digest 清单 `itemShowType` 恒 0、订阅 pending 无类型标注（下载后 meta 仍正确，文库卡片不受影响）。
- **列表阶段不可见文章预过滤失效**：`is_deleted`/`checking`/`ban_flag` 过滤移除（下载阶段兜底识别，但会在下载时才失败、而非列表时剔除）。

## 步骤

### A · `src/core/mp-client.ts`（核心：换端点 + 解析层）

- 端点常量 `APPMSG_PUBLISH` → `APPMSG = 'https://mp.weixin.qq.com/cgi-bin/appmsg'`。
