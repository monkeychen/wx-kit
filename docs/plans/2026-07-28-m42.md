## 关键判断:**不要把 CLI 细节再抄一遍进 compose**

compose 之所以能落后 20 个里程碑而无人察觉,**根因就是它把 CLI 知识抄进了自己文件里**
——抄来的东西不会跟着源头变。再抄一遍(哪怕抄得更全)只是把同一个 bug 推迟到下一次。

所以本次的做法是:

| | 归谁 |
|---|---|
| **在哪一步、用哪个能力、为什么** | compose(它是编排层,这是它的本职) |
| **参数、输出契约、环境差异、错误码** | **wx-kit-skill**(能力说明书,已随每次 CLI 变更同步) |

compose 里每条命令只给「最短可用形态 + 一句用途」,并显式写明**参数与输出以 wx-kit-skill 为准**。
这样下次 CLI 再变,要改的只有 wx-kit-skill 一处。

**推论:不拆 `references/`**。PRD 里写的「超过 ~150 行就拆」是防「流程被命令清单淹没」,
而按上面的分工,命令细节根本不进 compose,文件长不到那个量级。**拆目录反而会让人再往里抄细节。**

## 步骤

### A · compose 的「取素材」补上游(最缺的入口)

- **A1** 取素材从两条路扩成三条,并**按「用户手上有什么」排序**:
  1. **还没下载,只知道「昨天/某天各号发了什么」** → `subscription digest --date <YYYY-MM-DD>`
     → 按 `downloaded` 分流(已下的直接读,没下的 `download`)→ 再进选料。**这是 compose 此前完全没有的入口。**
  2. GUI 已导出 `exports/*.json`(不变)。
  3. CLI 现取 `library export`(不变)+ 补 `library search <关键词>`、`library list --sort/--order`。
- **A2** 显式提醒:`digest` 的日期**由 agent 自己换算**成 `YYYY-MM-DD`(CLI 不解析自然语言)。

### B · compose 的「读素材前先扫一眼」(新增小节)

**放在取素材与选题之间**——它影响的是「这批素材能不能用、该怎么用」,不是命令用法:

- `itemShowType`:`5` 视频消息 / `10` 文字消息**没有长正文**,正文只是一段描述;
  当写作素材时价值与图文完全不同,**选题前必须知道**,否则会基于一段描述编出不存在的论据。
- `warnings`:「下到了但可能不对」的唯一信号(未识别类型、正文疑似脚本)。
  **读到明显异常的正文时先看它**,别把解析坏的东西当素材。

### C · compose 的下游:定稿后可选发布

- **C1** 检查点 2 之后加一条**可选**下游:`site sync --ids <id> --slug <slug>` 发到个人站点。
- **C2** **必须写明「需用户明确要求才做」**——发布是不可逆的对外动作。
  这与既有两个 🛑 是同一条原则,不能因为「链路完整」就自动化掉。

### D · 保持不动(逐条核对,勿改坏)

两个 🛑 检查点、「选题轻量内联不调 hv-analysis」、「写作全权交 khazix-writer」、
「只经 CLI/导出文件取数,绝不读 library.json 或 import 代码」。
**补内容最容易把原本对的东西冲淡**,改完要逐条回读确认还在、且没被新内容挤到不显眼处。

### E · `agent/README.md` 同步

- 两个 skill 的一句话简介更新到当前能力(compose 不再只是「从已下载的开始」)。
- 供料契约一节:说明 `library export` 不再是唯一入口,`subscription digest` 是「还没下载时」的起点。
- 顺带核对 CLI 路径写法仍然正确(打包后 mac/win 的两种形态)。
