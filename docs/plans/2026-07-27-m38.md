# M38 实现计划 — 过滤读者不可访问的文章(v0.8.3 R1)

> 对应 `docs/PRD-v0.8.3.md` R1。分支 `feat/m38`。
> 过滤点只有一处(`fetchPage`),但**难点全在过滤之后**:count 要补齐、订阅水位不能被卡住、提示不能多嘴。

## 已核实的事实(2026-07-27 实测)

- **信号早就在列表里**:`appmsgex[]` 同一批状态字段中,能下的两篇 `checking: 0`,
  打不开的两篇 `checking: 1`;`is_deleted`/`ban_flag` 本例全为 0。M36 只读了 `is_deleted`。
- **打不开的页面长这样**:标题「此内容发送失败无法查看」,正文「此内容因涉嫌违…」。
  当前报错是 `invalid or unavailable article (no title parsed)` —— 兜底判定命中,原因笼统。
- **`checking: 1` 是终态**(安哥判定:审核不通过,非「审核中」)。
  **推论:被过滤的文章不会自己变回可见,所以订阅水位必须能越过它们**。
- **count 模式的补齐几乎是免费的**:`listArticles` 已按 `out.length >= range.count` 判断,
  过滤发生在 `fetchPage` 内则 `out` 自然只装可见文章、循环自然继续翻页。
  游标推进用的是 `pageLen`(**组数,未过滤**),不受影响。
- **`filteredOut` 有先例但语义不同**(M24 关键词过滤):那是用户主动指定的条件,报告合理;
  本次是系统行为,补齐成功时报告反而制造困惑(见 PRD 的纠正)。**必须用独立字段,不要复用。**
- `CrawlSummary` 现有字段:`ok/fakeid/listed/total/succeeded/failed/skipped/filteredOut?/items`。
- GUI 结果文案在 `AccountMode.tsx:105-109`。

## 步骤(bite-sized,TDD,每步跑 `npm test`)

### A · 过滤(`src/core/mp-client.ts`)

- **A1(红)** `tests/core/mp-client.test.ts` 加用例(扩 `tests/fixtures/appmsgpublish.json`,
  给 `checking: 1` 与 `ban_flag: 1` 各造一条,连同已有的 `is_deleted` 一起):
  - 三种状态的条目都不进 `ArticleRef[]`。
  - 正常条目(三个字段皆 0/false)照常返回。
  - `fetchPage` 返回值带出**被过滤条数**(供上层判断结果是否不及预期)。
- **A2(绿)** 抽具名判定,注释写清每个字段的来历:
  ```ts
  /**
   * 读者能否打开这篇文章。三个字段都来自后台列表,含义各不相同:
   *   is_deleted —— 作者自己删了
   *   checking   —— 审核不通过(终态;页面显示「此内容发送失败无法查看…涉嫌违规」)
   *   ban_flag   —— 封禁标记(未见真实样本,按字面处理:非 0 即不可见)
   * 这三种文章的页面都打不开,列进结果只会产生必然失败的下载。
   */
  function isReaderVisible(a: AppMsgEx): boolean
  ```
  `fetchPage` 返回 `{ items, total, pageLen, hidden }`。

### B · 补齐与上报(`listArticles` / `mp-crawl`)

- **B1(红)** `listArticles` 用例:
  - **count 模式**:第一页 5 条里 3 条不可见 → 继续翻页,**最终仍给满 count 篇**。
  - count 模式翻到底仍不够 → 返回已有的,不死循环(`begin >= total` 与空页保护仍有效)。
  - **日期范围模式**:窗口内的不可见文章被剔除,且**不因剔除而误判「已翻出窗口」**
    (终止条件看的是 `createTime < fromTs`,被过滤的条目根本不参与判断)。
  - 被过滤总数经 `ListOpts.onHidden` 回调上报(**不改 `listArticles` 的返回类型**,
    否则波及 crawl/ipc/cli 多处调用方)。
- **B2(绿)** 实现;`ListOpts` 加 `onHidden?: (n: number) => void`。
- **B3** `mp-crawl.ts`:收集 hidden 总数,`CrawlSummary` 增:
  - `unavailable?: number` —— 被过滤的篇数(有才带,数据层完整,agent 可读)。
  - `shortfall?: boolean` —— **结果是否不及预期**,判断收在 core 一处:
    count 模式 → `refs.length < range.count`;日期模式 → `hidden > 0`。
    渲染层只看这个布尔值,不各自重写规则(GUI 与 CLI 各判一次必然漂)。

### C · 提示(按 PRD 的三种场景)

- **C1** `AccountMode.tsx`:`summary.shortfall && summary.unavailable` 时才追加
  「另有 N 篇审核未通过或已下架,读者不可见」;补齐成功时**什么都不说**。
  与既有的关键词过滤文案并列时不重复啰嗦。
- **C2** CLI:`crawl` 的 JSON 始终输出 `unavailable`/`shortfall`(agent 自行判断),
  stderr 的人读提示遵循同一规则。

### D · 订阅链路(重点验「水位不卡」)

- **D1(红/绿)** `tests/core/mp-client.test.ts` + `tests/core/check-subscriptions.test.ts`:
  - `listArticlesSince`:最新几篇全不可见时,**仍能翻到水位并停下**,不无限翻。
  - `checkSubscriptions`:最新一篇不可见时,水位推进到**最新的可见文章**;
    **再查一次不得重复报同一批新文章**(否则每次检查都白跑一遍)。
- **D2** 被过滤条目写进订阅检查日志(诊断留痕),**不进用户可见提示**——
  日志是排查「这篇为什么没下」的唯一线索。

### E · 单篇下载的失败话术(`download-article.ts`)

- **E1** 手动粘一个违规链接时没有列表字段可依据,兜底判定保留;
  但识别错误页特征(页面含「此内容发送失败无法查看」/「已被发布者删除」等)时给具体原因:
  「该文章读者不可见(审核未通过或已被删除)」,而不是 `no title parsed`。
  **判定逻辑不动**(标题为空仍是唯一防线),只改话术。
