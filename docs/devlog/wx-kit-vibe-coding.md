## 0. TL;DR

一次会话里，从"分析一个原型"开始，走完了 **分析 → 头脑风暴对齐 → PRD → 实现计划 → 分子代理执行 → 两阶段评审 → 端到端验证 → 合并 → 跨会话续接文档** 的完整产品工程闭环，交付两个里程碑。

**成果数据**
- main 上 51 次提交，干净的语义化历史（feat / fix / docs / test / chore）。
- 62 个 vitest 单测 + 1 个 Playwright Electron 端到端测试，全绿。
- 两个里程碑（M1 核心层+CLI、M2 GUI）各自经 feature 分支开发、评审、合并。
- 产出文档：PRD、M1/M2 实现计划、AGENTS.md（含状态/路线图/陷阱）、本复盘。
- **评审与 e2e 共拦下 ~20 个真实缺陷**，其中 3 个是单测覆盖不到、只有端到端才暴露的硬坑。

**一句话心得**：Vibe-coding 不是"放飞地让 AI 写"，而是**用纪律化的流程把"感觉"约束成可验证的工程**——先定约束，再分步执行，每步都有 gate。

## 1. 全程时间线

### 阶段 1：分析原型，讲真话
用户：「分析一下该项目」。
我读完 `x-downloader`（Electron + React + Python 边车爬虫 + AnyProxy 代理 + 离线授权）后，没有只夸，而是直指问题：命名与产品不符、**三套抓取机制冗余**（代理捕获 / 隐藏窗口搜索 / Python Playwright 后台爬取）、授权只签 machineId 形同"防君子"、Python 服务默认绑 `0.0.0.0`、代理崩溃后系统代理不还原会让用户断网。判断这是 PyQt→Electron 迁移的历史包袱。

> 心法：**第一性原理 + 不谄媚**。分析的价值在于指出问题与本质，而非复述代码。

### 阶段 2：产品化需求 + 约束先行
用户明确：这是原型，要产品化为 `wx-kit`（微信百宝箱，第一阶段=下载器），需求=URL 多格式下载 / 公众号批量 / 浏览 md·html / 弃用代理，新仓库位置给定，**先出 PRD 确认再下一步**。

> 心法：**约束先行**。不直接写代码，先立"要做什么、边界在哪"。

### 阶段 3：头脑风暴，把模糊需求逼成明确决策
用 `brainstorming` skill，一次一个问题（多选），敲定了几个会重塑架构的分叉：
1. 代理弃用后批量爬取入口 → **扫码登录公众号后台 + 调图文接口**（唯一可行的非代理路径）。
2. 爬取技术形态 → **纯 Node/Electron 重写，去掉 Python 边车**（去掉 PyInstaller/Playwright/随机端口/0.0.0.0 一整套包袱）。
3. 浏览形态 → **应用内置阅读器**。
4. 授权系统 → **第一阶段不做**。
随后用户追加两条需求（多 URL 输入、面向 AI agent 的 CLI），又敲定：
5. CLI 运行形态 → **统一 Electron 二进制双模式（GUI/CLI）**，让 PDF（printToPDF）与扫码登录都能复用 Electron，零额外重型依赖。

> 心法：**为决策设计提问**。每个问题的答案都改变后续架构，所以一次一个、带推荐与理由。

### 阶段 4：PRD → 迭代 → 收敛开放问题
写出 PRD（定位/目标与非目标/F1–F5/格式规格/存储结构/架构/风控/里程碑/验收），用户审阅后追加（文章管理删除+按文件名搜索、下载进度信息），再把两个开放问题敲定（search 返回候选列表、文章库目录可配置且默认用户文档目录）。

### 阶段 5：实现计划（M1）
用 `writing-plans` skill。因第一阶段体量大，**按 PRD 的 M1–M4 里程碑拆成独立计划，先写 M1**（17 个 bite-sized 任务，含完整代码、TDD 步骤、运行命令、自检）。

### 阶段 6：分子代理执行 M1
用 `subagent-driven-development`：
- 先 `using-git-worktrees` → 用户选**就地开 feature 分支**（greenfield 不必 worktree）。
- 17 个计划任务归并成 ~8 个执行单元；**每单元：派一个全新 implementer 子代理 → spec 合规评审 → 代码质量评审 → 据评审修复 → 复验**。
- 纯逻辑严格 TDD；网络/Electron 部分注入依赖 + 手动验证。
- **端到端验证我亲自跑**（子代理沙箱解析不了 electron 二进制）：真实下载产出含合法 PDF、本地化图片、库索引；去重生效。
- `finishing-a-development-branch` → 合并 main，删分支。

### 阶段 7：M2（GUI）同流程
先问 UI 栈（选 **Antd 6 + Tailwind**）→ 写 M2 计划（10 任务）→ 分子代理执行：应用壳、三个可测接缝（Settings/wxfile 协议/读文章）、IPC 桥、下载页、文章库页、阅读器、设置页。每单元两阶段评审。我做 electron 启动冒烟 + 自动化验证。合并 main。

### 阶段 8：把"手动 GUI 验证"也自动化
用户追问「不能自动化测试吗」。我用 **Playwright 的 `_electron` 驱动器**写端到端：启动真实应用、对内置 fixture 服务跑「下载→文章库→阅读器→删除→设置」，**断言阅读器图片 `naturalWidth>0`** 来证明 `wxfile://` 协议确实把本地图片喂进了页面。过程中抓到一个**测试选择器**的坑（Antd v6 会在两汉字间插空格，"阅 读"），修正后全绿，合并为回归测试（`npm run test:e2e`）。

### 阶段 9：跨会话续接
用户问记忆文件在哪、要不要写 AGENTS.md、进度怎么记。我发现一个真实缺口：**`.claude` 记忆绑定在当前会话的 cwd（x-downloader），不随 wx-kit 目录走**，新会话读不到。于是把**仓库内 `AGENTS.md` 设为权威**（状态表/路线图/已定不可回退决策/命令/已知陷阱/文档索引），`CLAUDE.md` 软链到它，`.claude` 记忆瘦身成指针——单一真相源跟着仓库走。

> 心法：**连续性靠仓库，不靠会话记忆**。

## 2. 关键决策与理由

| 决策 | 选择 | 为什么（对用户/工程的影响） |
|------|------|------|
| 抓取入口 | 扫码登录后台 + 图文接口 | 代理弃用后唯一稳定的非代理路径 |
| 爬取技术形态 | 纯 Node/Electron 重写 | 去掉 Python/PyInstaller/独立 chromium/数据库——单语言单进程单二进制，打包/签名/维护都简单 |
| CLI 运行形态 | 统一 Electron 二进制双模式 | 一套能力（PDF、登录窗口）GUI/CLI 共用，零额外重型依赖；CLI 输出纯 JSON 服务于 AI agent |
| 浏览 | 内置阅读器 | 体验不跳出；md 用 react-markdown，html 用沙箱 iframe |
| 授权 | 第一阶段不做 | 开箱即用，先把核心做扎实 |
| 本地图片 | 自定义 `wxfile://` 协议 | 让相对图片正确显示，且不放开 webSecurity |
| 文章库 | 文件系统 + library.json | 第一阶段够用，便于用户直接拷走，不引数据库 |
| 进度 | download-queue 单一来源 | GUI 经 IPC 流式、CLI 走 stderr，stdout 只输出最终 JSON |

## 3. 工作流：每个 skill 把守一道关

```
分析 → brainstorming（意图/边界）→ PRD（确认）
   → writing-plans（按里程碑拆，bite-sized + TDD + 完整代码）
   → using-git-worktrees（隔离工作区）
   → subagent-driven-development（每任务：实现 → spec 评审 → 质量评审 → 修复 → 复验）
   → 端到端验证（控制者亲自跑 electron）
   → finishing-a-development-branch（合并/收尾）
   → AGENTS.md（跨会话续接）
```

每一道都是 gate：不确认不写码、不评审不算完、不验证不声称完成。这把"vibe"约束成了可重复的工程。

## 4. 评审 / e2e 拦下的真实缺陷清单

**单测全绿 ≠ 没问题。** 价值最高的发现来自两阶段评审和端到端：

**代码质量评审抓到的（节选）**
- 文件名按 UTF-16 截断会劈裂 emoji 代理对 → 改按码点截断。
- Markdown frontmatter / HTML 转义不全（换行、反斜杠、`"`）→ 补全转义。
- `library.json` 损坏会抛不可读异常；`remove()` 用 `rm -rf` 却不校验目录是否在库根内（可能误删任意路径）→ 加清晰报错 + 根目录containment 守卫。
- CLI `--help` 会污染 stdout 的 JSON 契约 → 重定向到 stderr。
- 窗口下载中途关闭 → `event.sender.send` 崩溃 → 加 `isDestroyed()` 守卫，并让下载在窗口关闭后仍跑完入库。
- 阅读器 `toWxfileBase` 兄弟目录前缀误匹配 → 加分隔符边界。
- 设置保存/库加载/删除无错误反馈 → 补 `message.error`（反馈引导行动）。

**只有端到端才暴露的 3 个硬坑**
1. **`node:sqlite` 崩溃**：cheerio 依赖 undici，其 sqlite-cache-store 在加载时静态 `require('node:sqlite')`，被打进 bundle 后 Electron 31 的 Node 没这个内置模块，主进程加载即崩。→ vite 配置 external undici（我们只用 `cheerio.load`，让它惰性永不加载）。
2. **无效文章误报成功**：微信对已删除文章返回 HTTP 200 错误页，抓取"成功"但字段全空。→ "解析后标题为空即视为无效文章"判定为失败。
3. **PDF 窗口触发自动退出**：printToPDF 的离屏 BrowserWindow 关闭时，Electron 默认"无窗口即退出"被触发，与后续的入库/输出竞速，导致进程提前终止。→ CLI 模式注册 no-op `window-all-closed`。

**e2e 自身的坑**：Antd v6 在两个汉字按钮文本间自动插空格（"阅 读"），导致 `has-text("阅读")` 匹配失败——是测试选择器问题，不是应用问题（截图佐证应用正常）。

> 心法：**对可测的逻辑 TDD，对网络/Electron/GUI 用注入+端到端**；声称"完成"前必须有证据（`naturalWidth>0`、退出码、落盘文件、截图）。

## 5. 可复用的 Vibe-Coding 心法（总结）

1. **约束先行**：先 PRD/计划/规范，再写码。没有规范的工作空间不动手。
2. **一次一个决策**：模糊需求用"带推荐+理由"的单选逐个敲定，别一次甩一堆选项。
3. **按里程碑切薄**：大项目拆成"各自能交付可运行软件"的里程碑，每个独立出计划。
4. **分子代理 + 两阶段评审**：实现与评审分离；spec 合规防过度/欠缺，代码质量防 bug。
5. **TDD 用在刀刃上**：纯逻辑 TDD；难测的（GUI/网络/Electron）用依赖注入 + 端到端断言。
6. **控制者补位**：子代理沙箱跑不了的（真实 electron），控制者亲自验。
7. **诚实压倒顺滑**：发现"AGENTS.md 没完全包含记忆内容"就直说并补齐，不糊弄。
8. **连续性写进仓库**：状态/决策/陷阱放 AGENTS.md，跟着 git 走，任何会话任何 agent 可读。
9. **干净的提交历史就是文档**：51 个语义化 commit 本身就是一份可追溯的施工日志。

## 6. 可对外分享的几个"钩子"

- "AI 写代码不可怕，可怕的是没人给它定约束。这次全程没让它放飞，每一步都有 gate。"
- "单测全绿那一刻最危险——真正的 3 个硬坑（sqlite 崩溃、假成功、PDF 截断）都是端到端才抓到的。"
- "让 AI 自己审自己：一个子代理实现，另两个子代理分别审'做对了吗'和'做好了吗'。"
- "跨会话续接别靠 AI 的记忆——它的记忆绑在目录上、不可移植。把真相写进仓库的 AGENTS.md。"
- "产品化一个原型，第一步不是写代码，是指出原型哪里是历史包袱、该砍什么。"

## 7. M3 增补：登录 + 公众号批量爬取（CLI 优先，2026-06-07）

接续 M1/M2，第三个里程碑把"批量爬取"这个真正的差异化能力做了出来。几条值得记的：

- **范围先切，不贪大**：PRD 的 M3 含 GUI 批量页，但选了 **CLI 优先**——先交付无头核心 + CLI（agent 可调），GUI 批量页拆成 M3.5。复刻 M1→M2 的节奏，最快拿到可用能力，且核心可单测。
- **最高风险前置成 gate**：M3 唯一真不确定的是"原型 2026-02 抓的 mp 接口到 6 月还活着吗"。于是计划第 1 步就是**活体验证 spike**：扫一次码 + 调一次 `searchbiz`，肉眼确认 `ret:0`、字段名对得上，**再往下建**。证明接口活着才写后面九个任务，不白搭架子。
- **用 Electron 自带能力替代原型的重依赖**：原型用 Playwright + 独立 chromium 扫码登录（还有一大坨找系统 Chrome 的 fallback）。本项目直接用 `BrowserWindow` 载入登录页 + 监听导航抓 `token`、`session.cookies` 取 cookie——**贴合"无 Python、无独立浏览器"的既定决策**，代码还短得多。
- **纯逻辑注入 + 真实数据当 fixture**：`mp-client`/`mp-crawl` 只依赖注入的 `mpFetch`，离线可单测；测试直接拿原型 `data/articles/*.json` 的真实返回形状当 fixture。爬取层只负责"发现 URL"，落盘 **100% 复用 M1 的 `downloadArticle` + `DownloadQueue`**——列到 URL 即喂队列，去重/失败不中断/汇总全白嫖。
- **风控写进类型**：`ret=200013→RateLimited`、`200040→AuthExpired` 映射成具体异常；列表阶段命中频控指数退避（30s×3）；下载间随机 2–5s。
- **教训：fixture 必须贴真实数据形状**。两个测试当场翻车都不是实现错，是假数据失真——① 分页 fake 用 `begin/20` 索引却设 `total=4`，而真实接口 `count=20/页` 一页就返完，循环正确地停了；② `library.json` 是 `{version,articles:[]}` 包裹，我图省事写成裸数组，`.articles` 取到 `undefined`。**假数据偷懒，测试就帮倒忙。**
- **真实账号端到端收尾**：本地真登录 + 爬 2 篇（`--fakeid` 绕开"腾讯"多候选的歧义守卫）→ `succeeded:2, failed:0`，content.md/meta/本地图片全落盘。自动化测不到的真链路，靠这一步坐实。

> 一句话：**先证明外部接口活着，再写代码；能复用上个里程碑的就别重写**——M3 的下载链路一行没动 M1。

## 8. M3.5 增补：批量爬取 GUI（2026-06-07）

把 M3 的 CLI 能力接成给非命令行用户的 GUI 页。重点不在功能（功能 M3 已验），而在交互。

- **交互决策走"可视化伴侣"逐屏定**：开了浏览器版伴侣，把三个关键交互做成线框让安哥点选——① 单页渐进 vs 分步向导 → 选单页；② 整页登录引导 vs 顶部状态条+禁用 → 选整页引导（没登录就只给"去登录"一件事，不摆点不动的控件）；③ 实时逐篇列表 vs 极简进度 → 选实时（慢任务越透明越安心）。**比纯文字描述快得多，也避免我猜错方向白写。**
- **核心层只开两个小口子，其余全接线**：`DownloadQueue` 加可选 `shouldContinue`（取消，URL 下载页不传、行为不变）；`mp-crawl` 加 `onListed`/`onItem` 逐篇上报。爬取/落盘逻辑一行没动 M3。
- **"列表先铺、逐篇翻状态"**：crawl 一拿到 `appmsg` 列表就把全部标题整批推给渲染层立刻铺行（"等待"），再逐篇翻 ⟳→✓/⊘/✗。ETA 纯前端用"已完成/已耗时"估，不进后端。
- **取消=停后续、已下保留**：和去重续传天然兼容，省掉了"暂停/恢复"这套状态机（YAGNI）。重试单篇直接复用现有 `download` 接口，不造新东西。
- **安哥的一句话改了测试策略**："session 落盘后过期前你完全可以自动化"。于是把"真链路全靠手动"降级为"半自动"——验证脚本把本地缓存的 session 拷进隔离 userData，Playwright 驱动真实 GUI 搜号 + 爬 2 篇，断言实时行变"成功、成功"，全程无人扫码。只有 session 失效才需人工。**凭证留 userData（本地不同步）而非库根，是安全与"统一可配置"权衡后的选择。**
- **教训延续**：两个测试当场翻车仍是 fixture 失真（分页 begin/20 设错 total、library.json 包裹格式），不是实现错——假数据偷懒，测试就帮倒忙。

> 一句话：**UI 的"形"用可视化伴侣和安哥对齐，"魂"（取消/重试/实时）靠把核心层的两个小钩子接出来**——大头还是复用，不是重写。

## 9. M4 增补：electron-builder 打包（2026-06-07）

第一阶段最后一块拼图——把 wx-kit 打成可分发的 mac/win 安装包。

- **签名/公证先不做**——未签名包够用且贴「开箱即用、不加门槛」的阶段定位。代价是首次打开有系统警告，靠 README 写清放行步骤（mac 右键→打开 / `xattr -cr`；win SmartScreen→仍要运行）。"反馈引导行动"原则在这里延伸到了分发环节。
- **图标先截图签收、再定代码**——"宝盒"这个概念一开始就交给安哥过目再实现：先渲染了第一稿（拱盖像侧视、视角打架），安哥一指出，我重画成"箱体等宽的正面拱顶 + 金属带贯穿"，再渲染、确认、才提交 `build/icon.png`。**产品脸的决策权在用户手里，不在 AI 的猜测里**。

## 11. M6 增补：下载闭环 + 下载历史（2026-06-08）

把"能下载"补成"下完能确认、能找回"。两个需求 R1（就地确认/阅读）+ R2（历史）被**合并成一个组件**而非各做一套。

## 12. M7 增补：反馈引导——把"静默"点亮成"看得见"（2026-06-08）

R5 的本质不是加功能，是把系统已有但藏起来的状态**翻译给用户**。core 早就在频控时退避 30/60/90s、早就抛出各种错误，只是 GUI 把这些咽了。M7 做两件事：让退避可见、让失败可行动。

- **先确认 bug 再动手**：这个里程碑由安哥一个真实 bug 引出——「猫笔刀 2026-05-24~27 下载 0 篇」。没有猜，写了 spike 打真实 API，实测出 `appmsg` 每页只回 5 篇而代码 `begin += 20`（固定步长）每页跳过 15 篇。TDD 用「5 篇/页」模型复现并锁死，`begin += pageLen`（原始返回篇数）修复，真实 API 验证窗口正确返回 2 篇。**频控/分页这类外部契约，实测一次胜过读十遍文档。**
- **可见的退避，不是进度条**：退避是"在等"，不是"在做"，所以用独立朱砂横幅 + 客户端每秒倒数（「约 N 秒后重试 · 第 k 次」），非报错红——传达"系统在替你扛频控、还要等多久"，而非"出错了"。core 加一个 `onBackoff` 回调上报，IPC 透传 `{kind:'backoff'}`，渲染端拿 `until` 自己倒数。**反馈要引导行动（等着就好），不是只报状态。**
- **错误话术归一，且放对层**：原始 `fetch timeout after 20000ms`、`invalid or unavailable article` 对用户是噪音。`explainError` 把它们按 code + message 关键字两路归一为「人话标题 + 下一步」（登录过期→去登录、网络超时→查网络、文章无法访问→可能被删），原文折叠在 tooltip 备查。**放哪一层是第一性问题**：它是纯展示逻辑，CLI 契约是 JSON 给 agent 解析、本就不要人话——所谓"core 共享"是 YAGNI，放 `src/renderer/error-explain.ts` 才不破"renderer 绝不 import core 运行时"的边界（现有 renderer→core 全是 `import type`，我差点成为唯一的运行时 import）。
- **验证戳破了一个伪需求**：原计划给"完成/取消后回到配置"加「返回配置」按钮（R3 残留）。真实 session 截图时按钮的 testid 等不到——因为 `await mpCrawl` 完成即 `setRows([])`、配置卡本就自动重现，按钮只在 done 事件到 promise resolve 间闪现 200ms。**端到端验证当场证伪了一个我以为要做的功能**，撤掉，R3 标记"既有流程已满足"。
- **逼出隐藏元素也要看真实渲染**：退避横幅和失败行话术要真实 200013/失败才出现，没法按需触发。没有用"逻辑测过就算了"糊弄——临时种态（改初始 state→build→截图→还原）把两个元素逼到真实渲染里看了一眼确认无误，再还原。遵守 M5 立的规矩到底。

> 一句话：**M7 把"后端在忙什么"老实告诉用户**——退避不再像卡死，失败不再甩英文报错。最贵的一课来自一个真实 bug 和一次证伪：**实测胜过臆测，验证能反过来砍需求。**

## 13. M8 增补：PDF 防跨页切断（R4，2026-06-08）

一行需求「PDF 里图片别被页边界切断」，做法上有两条路，选型决定了它放哪、影响谁。

- **`@media print` 注入 HTML，而非 `insertCSS` 注入窗口**：PDF 走的是 `printToPDF` 加载保存好的 `index.html`。把防切断规则作为 `@media print` 加进 `buildHtml` 的内联样式——随 HTML 走、只在打印态生效（屏幕阅读器零影响）、用户自己 Ctrl+P 打印这份 HTML 也受益，还能在纯函数 `buildHtml` 层 TDD，让依赖 electron 的 `export-pdf.ts` 一行不改。比起在离屏窗口 `insertCSS`（PDF-only、HTML 不沾），前者自包含、可测、红利更多。
- **验证戳破了自己的假设**：本想用「一张高图」做有/无规则对照，结果发现 **图片是「替换元素」，Chromium 默认就把放不下的整张图下移、根本不切**——裸图对照看不出差别。真正会被默认拦腰切断的是**代码块/表格**（普通块容器，默认随意分页）。于是把对照换成一段会跨页的 `<pre>`：无规则版切到第 17 行、有规则版整块下移次页完整。**做验证时别假设 bug 长什么样——亲手把它复现出来，假设常常是错的。**
- **端到端兜底**：e2e 默认格式不含 pdf，R4 没有自动化像素断言，就用「真实文章 CLI 出 PDF + 用 poppler 渲染翻页目视」端到端兜——这类依赖 electron/Chromium 的保真问题，单测断不了像素，眼睛和真实出件才是终审。

> 一句话：**M8 最大的收获是验证而非编码**——一行 CSS 规则，却靠「亲手复现 bug」纠正了「图片会被切」的错误直觉，定位到真正受益的是代码块/表格。

## 14. M9 增补：文库组织 + 卡片/列表视图（2026-06-08）

把文库从「只能搜+删」做成可治理的藏馆：排序、按公众号筛选+分组、批量删除；安哥又追加了「访达式列表视图」。

### M9 后：把 e2e 扩成 M5–M9 全功能回归套件，顺手逮到真 bug

安哥要「所有功能点都测过去、完善 e2e」。把原本只覆盖「URL 下载→阅读→删」的 e2e 扩成 24 条断言的多文章回归套件（夹具跨 2 公众号 + 一篇无标题失败页），覆盖：历史就地确认/复制下载项/已存在跳过/失败重试、设置库根、文库排序/筛选/分组/卡片⇄列表/双击阅读/批量+单篇删除、真实公众号抓取。过程踩了三个有价值的坑：

- **e2e 逮到一个真实 UX bug**：双击列表行进阅读总是失败、只选中 1 篇。根因不是测试写错——是**单击选中后批量条插入、把列表向下挤**，双击的两次点击跨越了这次重排、第二下点偏了。**真人双击同样会中招**（两次点击落在同一屏幕位置，但内容已下移）。正解不是改测试，是把批量条改成**底部浮动条**（不再 reflow）。自动化测试替我发现了肉眼演示时没注意的交互缺陷。
- **夹具按路径区分文章**：`articleId` 回退按 `origin+pathname` 归一、**忽略 query**，于是 `?id=a1/a2` 全撞成一篇——必须用不同**路径** `/article/a1`。这恰好暴露了「断言只数历史行数、没数文库实际篇数」的盲点：3 行里其实 2 篇是跳过的。
- **antd v6 的两个选择器坑**：Select 的可点根是 `.ant-select`（不是 v5 的 `.ant-select-selector`）；按钮文本被自动插空格成「删 除」，`has-text("删除")` 匹配不到、得用单字「删」（这条 AGENTS.md 早记了，这次又踩）。

> 一句话：**e2e 不只是回归网，还是 bug 探测器**——它替我发现了「选中即重排」这个肉眼演示漏掉的真交互缺陷，催出了底部浮动批量条。

## 15. v0.2.1 增补：依赖安全审计——把 26 个 Dependabot 清零（2026-06-09）

v0.2.0 发布后 GitHub 报 26 个 Dependabot 漏洞。一个看似「升级版本号」的小活，真正难点全在**国内网络环境**，逼出几条可复用的工程教训。

- **先看清「真漏洞」再动手**：26 个全是 `package-lock.json` 的**间接依赖**。真能动手的只有直接依赖：electron / vite / vitest / electron-builder。Round 1 先升 vite v6 + vitest v3 + electron 38（每个 bump 后跑 119 单测 + tsc + lint + e2e），收掉 16 个。剩 10 个（electron 3 + tar 6 + glob 1）要跨大版本。
- **「单测全绿 ≠ 升级安全」，打包正确性靠真实启动**：electron 跨大版本（31→38→42）最怕 `undici external` 失效（cheerio 间接依赖 sqlite-cache-store 静态 `require('node:sqlite')`，打进 bundle 会让主进程加载即崩）。e2e 走的是 `vite dev`、不覆盖打包后的 .app。所以每次大版本跳，都**真实启动打包后的 `wx-kit.app` + 触发 cheerio 解析路径 + 断言零 console/page 错误**——这是 M4 立的规矩，在 electron 42 上再次兑现。
- **最大的坑是网络，不是代码**：本机常驻死代理 `http_proxy=8118`。`@electron/get` 用 Node 24 内置 `fetch`(undici)，它**默认不读 `http_proxy`**、直连 github 在国内不可达 → `UND_ERR_CONNECT_TIMEOUT`；走 8118 拉 130MB 又**中途截断**。**正解：electron 二进制走 npmmirror 国内镜像 + 给镜像域名加 `no_proxy` 直连**（cdn.npmmirror.com ~1.5MB/s 稳），代理保留 set。安哥据此立了项目规则：npm/二进制走国内镜像优先、代理只兜底。
- **坑中坑**：本机**没有 `timeout` 命令**——`timeout 12 curl …` 静默报 command-not-found 让 curl 根本没跑，误判「镜像 0 字节不通」，差点把唯一正解否掉。验证下载只能用 `curl --max-time`。
- **方向反转的第二条规则**：二进制下载要镜像+保留代理，但 **`gh`/`git push` 到 github 反而要 unset 代理**——8118 代理传 github 大文件同样卡死（单个 140MB release 资产传 10+ 分钟零字节），直连才稳。安哥实测后补进规则。
- **证伪一次冒进**：升级中途一度想「electron 42 + builder 26 全跟 latest」，但在「代理拉不全二进制」时我误判为「本机环境物理不可解、回滚」。其实是镜像方案没用对（`timeout` 坑 + 没配 `ELECTRON_MIRROR`）。**环境问题也要找根因，别急着判死刑**——换镜像后一次过。

> 一句话：**这次没写几行代码，难的全是「让正确的包从正确的源、用正确的代理策略、完整地下到本地」**。最后 28 个 Dependabot 全部 `fixed`、0 残留 0 忽略（升级中 GitHub 又新录 2 条 electron advisory 一并被 42 覆盖）。教训沉淀成项目规则（AGENTS.md）+ 记忆，比清零本身更值钱。

## 18. M11 公众号订阅：单进程桌面应用里做「类 RSS」（2026-06-16）

v0.3.0 的大头。难点不在写代码，在**在「单进程、无后台、会过期的登录态」约束下，把 RSS 那套订阅语义做得诚实**。

- **设计阶段就被一条数据约束改了形**：已下载文章只存公众号名、不存 `fakeid`，而轮询新文章必须有 fakeid。fakeid 只在「按公众号抓取历史」和「搜号结果」里有 → 订阅列表只能由这两处派生，纯 URL 下载来的号进不了。这条在 brainstorming 读代码时就发现并写进 spec，避免了实现到一半才撞墙。
- **把「会动的」全部纯函数化、注入化，副作用留在最外层**：核心三件套全部可单测——`subscriptions`（存储 + `accountsFromHistory`/`mergeAccounts` 派生）、`subscription-schedule`（`shouldCheckNow` 纯判定，覆盖「到点触发/已检查跳过/启动补检」各分支）、`check-subscriptions`（注入 `listFn`，断言新检测/水位推进/频控退避/单号失败隔离/登录失效中止）。主进程的 scheduler 与 IPC 只做「读配置 → 调纯判定 → 触发 → 写盘 → 发事件」的编排，不含可分支的业务逻辑。17 条新单测，主进程接线靠 build + e2e。
- **诚实约束写进代码也写进文案**：定时**只在 app 开着时生效**——这是单进程桌面应用的物理事实，不假装有后台。`scheduler.start()` 立即 tick 一次做「启动补检」（当天时刻已过且未检查就补一次），`shouldCheckNow` 的「lastCheckedAt < 今天 slot」分支专门覆盖它；订阅页文案直说「关闭时错过的检查会在下次启动补做」。登录态会过期 → `checkSubscriptions` 撞 `MpAuthExpired` 整体中止、不静默吞，主进程置 `subsAuthExpired` 标志、订阅页弹登录引导横幅。
- **水位语义防「存量当新文章」**：订阅那一刻把水位设为该号当前最新文章的 `createTime`（取不到就用「现在」秒），只有之后发布的才算新；每次检查后水位推进到本次最新。否则一订阅就把人家几百篇历史全标成「新」砸出来。
- **计划里给 UI 留口子、执行时按真实代码接入**：`Settings.tsx` 的写法我写计划时没读，于是计划只说「按其既有 state/persist 模式接入、控件代码给全」。执行到那步先读——发现它是「单个 `s` 状态 + 一个『保存设置』按钮统一持久化」，而非我设想的逐控件 `persist()`。按真实模式接（`setS({...s, field})`），没硬塞第二套状态。**计划对未读文件的假设要标成「待对齐」，别写死。**
- **e2e 在不依赖网络的边界上验**：订阅检查要真 session，e2e 聚焦「不需要网络的部分」——导航项位置、订阅页可达/渲染（列表或空态）、检查更新按钮存在、设置三控件存在。恰好 e2e 的 account-mode 用真实缓存 session 抓了一个号，于是订阅页真的走了一遍「从历史派生账号」的活路径，零 console 错误。
- **收尾自动化**：143 单测（+17）全绿、e2e 全绿后自动合 main、删 `feat/m11`、八个任务逐一 commit；PRD §4 R2 九条验收逐条勾，并诚实标注「真实壁钟到点的整链 e2e 测不了、由构成逻辑单测兜底」。

> 一句话：M11 的价值是示范了「**约束驱动设计**」——单进程 + 无后台 + 登录会过期这三条物理约束，决定了订阅必须是「opt-in 的、app 开着才跑的、过期要明示的、启动会补检的」，而不是照抄服务端 RSS。把这些约束写进 `shouldCheckNow` 的分支和页面文案里，比假装它是个常驻服务诚实得多。

## 19. M12 订阅触发升级 + 检查可观测性（2026-06-16）

安哥用了 M11 订阅后两问：① 能不能按小时而非只能按天查？② 怎么知道定时真跑过？前者扩触发机制，后者补可观测性。一次里程碑两件。

- **「间隔从何时起算」用户选了网格锚 0 点，我照办但留了诚实约束**：每隔 N 小时 = 每天从 0 点切 N 小时网格（N=6 → 0/6/12/18）。N 不整除 24 时末段不足 N 小时，当天在次日 0 点收口重置——`nextScheduledInstant` 用 `min(候选, 次日0点)` 处理，单测专门覆盖 N=5 now=22:00 → 次日 0 点。没假装能精确均匀分布，这是单进程桌面 app 的事实。
- **判定统一成一句抽象**：`lastScheduledInstant(now, config)` = 当前已过的最近计划时刻；`shouldCheckNow` = 该时刻存在且 `lastRunAt < 它`。daily 在今天时刻前返回 null，interval 恒有最早当天 0 点。这一个抽象同时涵盖了 daily/interval 两种模式 **和** 启动补检（app 没开着错过某网格点，启动时 now 已过该点且 lastRunAt 早于它 → 补一次）——三件事一个函数收口，比写三段分支干净。
- **可观测性的关键判断：日志放哪**。放文库目录会污染用户浏览的内容、且那是「下载产物」的归属；放 `userData`（与 `mp-session.json` 同处）是「诊断数据」的归属。所以 `subscriptions.json` 只留最近 50 条驱动页面、全量落 `userData/subscriptions-check.log`。**数据按语义归类，不按技术层堆放。**
- **写盘失败不阻断主流程是硬约束**：`logCheck` 整体 try/catch——日志是「锦上添花的留痕」，磁盘满/权限错时不应让订阅检查本身失败。这条直接对应 spec 的错误处理段，不是事后补的。
- **触发器参数化（auto/manual）一笔带过却关键**：`runSubscriptionCheck(trigger)` 让定时走 `'auto'`、手动「检查更新」走 `'manual'`，检查记录里能一眼区分「这是我点的」还是「定时自己跑的」——这正是回答安哥「怎么知道定时生效」的直接证据：开了自动检查、到点后检查记录冒出 `auto` 条目。
- **文档全程同步、不是事后补**：安哥专门叮嘱「记得更新 PRD 等」。M12 从设计到合入，PRD R3 需求 + §4 验收七条逐条勾、ROADMAP 状态与索引、devlog §19 一起进。每个里程碑交付 = 代码 + 文档对账，不留「文档漂移」债（呼应 §16 的教训）。

> 一句话：M12 的方法论是**「把会动的判定抽成一个纯函数、把留痕和主流程解耦、数据按语义归类」**——daily/interval/启动补检三种触发语义被 `lastScheduledInstant` 一个抽象吃掉，日志写盘失败被 try/catch 隔离不连累检查，诊断日志归 userData 而非文库。单进程桌面 app 的约束照样能把「类 RSS」做得可见、可控、诚实。

## 20. UI 一致性打磨：四个页面栏宽统一（2026-06-16）

v0.3.0 收尾后安哥扫了一眼 UI：下载、设置两页左右留白大，订阅、文库两页却贴边——切页面时内容栏宽度跳变。一次小打磨。

- **方向让安哥定，给推荐**：统一成满宽还是统一成居中窄栏，是观感取舍（文库的卡片网格/列表表吃宽度，表单怕散）。安哥选满宽——四个页面去掉 `.page-narrow`、都只留 `.page` 的 40px 内边距。一刀切齐，最省心。
- **视觉一致性用测量验证，不靠肉眼**：截了四个页面的图后，没凭感觉判「看起来一样了」，而是用 Playwright `getBoundingClientRect` 量每个页面 `.fade-in` 的 left/width——改前下载/设置 width=860 居中（左右各空 ~170）、订阅/文库满宽；改后四个全部 left=40 满宽起步。**「看起来一致」是主观，「left 全等于 40」是客观**。视觉回归该尽量量化。残留的 11px 宽度差（1109 vs 1120）也查清了：是内容多寡导致有的页面出了滚动条，不是栏框不一致。

## 21. 频控韧性 + 去规律化：从「治标」到「治本」（2026-06-18~22）

安哥连发几问把频控这条线逼到了根上：① 按公众号下载时频控 retry，点取消没用；② 订阅被限时还在 retry 吗，有就取消；③ 订阅太规律，容易被识别，怎么优化？三问串成一条从「让取消生效」到「别火上浇油」再到「别长得像机器」的递进。

- **取消失效的根因是「信号够不着」，不是「按钮没接对」**：用 systematic-debugging 定位——按公众号下载分列表/下载两阶段，取消信号只在下载阶段的 `DownloadQueue` 循环开头被查；而频控 retry 发生在**列表阶段**的 30/60/90s 指数退避 `sleep` 里，那段干等根本没看取消标志。所以点了取消、标志也置上了，但代码正卡在 sleep 里，要等退避跑完（最坏 ~3 分钟）才理你。修法：串入 `AbortSignal`，退避等待用 `abortableWait` 让「sleep 与取消竞速」，一取消立即返回；IPC 从 `cancelRequested` 布尔换成 `AbortController` 让信号能传进退避。`mp:crawl:cancel` 频道名不变 → 渲染层取消按钮一行没改。**先写「卡在退避里点取消」的失败测试（模拟永不 resolve 的 sleep）复现卡死，再修。**
- **订阅的频控 retry 是「火上浇油」，直接删而非优化**：订阅检查命中频控原先也退避重试 3 次。但回到第一性问题——重试是在**已经被限的登录态**上继续追加请求，只会刷新/延长冷却窗口，是反效果。所以不是「优化退避曲线」，是**根本不该重试**：命中即把该号记为本轮失败、跳过，等下一轮定时检查自然再来。连带删掉因此变成死代码的 `onBackoff`。**正确的频控应对是「停手等冷却」，这恰好也是 ①「取消能即时停」的价值所在。**
- **去规律化要分清「真指纹」和「治标剧场」**：先把当前的机器指纹列清楚——每天同一秒触发、固定 fakeid 顺序、**恒定 2.0s 账号间隔**。三个里恒定间隔最像机器（人不可能分毫不差 2 秒）。对症加抖动：间隔 `2000→randMs(3000,8000)`、触发时刻叠加确定性顺延、账号顺序每轮打乱。**但我对安哥说了实话：抖动削的是「明显机器节奏」这个把柄，挡不住高频轮询本身——微信频控第一身份是登录态（账号+token+cookie）+ 请求量/频率，IP 和节奏是次要信号。真正的大杠杆是降频率/减账号数。抖动是锦上添花，不是免死金牌。** 不夸大疗效，是这条线最该守住的诚实。
- **「确定性抖动」是 B 的关键设计**：触发时刻的随机顺延**不能每次轮询重算**——否则 `shouldCheckNow` 会抖成早触发/重复触发。做法：偏移由「时段起点」经整数哈希确定性派生（同一时段恒定、日间/段间各异），只往后顺延 0~30min（不会早于设定点）。且**现有网格函数一行没动**（旧测试全绿），新增 `scheduleJitterMs`/`shouldRunCheck`（在 `shouldCheckNow` 上叠抖动闸门、去重仍按原始时段 key 防双触发）/`nextCheckAt`（显示用），scheduler 与页面「下次预计」切到新函数。**加特性靠新增纯函数包裹，不改既有契约。**
- **「砍 count 减频控」被当场证伪**：安哥曾提议把订阅回看篇数从 20 砍到 3 减频控。回到机制——`listArticles` 单页 `pageSize=20`，count≤20 时**一页拿完、不翻页**，所以 count=3 和 count=20 对微信都是**同 1 次请求**，频控压力一样；而 20 是「回看窗口」，砍小了某号一次群发超过窗口数就会**永久漏文章**。结论：**零收益、纯增风险**，保持 20。这条已沉淀进 memory，免得日后又被当频控手段重提。

> 一句话：频控这条线的方法论是**「先找信号够不着的根因（取消），再回第一性删掉反效果的重试（别火上浇油），最后对真指纹加抖动且不夸大疗效（去规律化）」**——三步都用失败测试先复现、用确定性设计避免引入新抖动 bug、用机制分析证伪「砍 count」这类想当然的治标。

## 22. 阅读器 Markdown 标题重复：修在「谁该负责」那一层（2026-06-22）

安哥发现文库里读文章，md 视图标题出现两次。一个小 bug，但定位修在哪一层有讲究。

- **根因是两处都「尽职」地渲染了标题**：`buildMarkdown` 在正文顶部注入 `# <title>`——这是对的，导出的 `content.md` 用 Obsidian/编辑器打开时需要标题。而阅读器自己也渲染了一套标题头（kicker + h1 + byline），于是 ReactMarkdown 把正文那行 `# <title>` 渲成第二个 h1。**不是谁写错了，是文件态与阅读态对「标题」的需求不同。**
- **修在表现层，不动磁盘文件**：.md 文件该留标题（对外部工具有用），重复只发生在「阅读器既画了自己的标题头、又渲染了带标题的正文」。所以让阅读器在渲染前剥掉那行——新增纯函数 `stripLeadingTitle`，只在「开头第一处非空内容恰为 `# <title>`」时剥离，正文里真实的同名小节、非首行标题都保留。7 条单测覆盖（含 CRLF、前导空行、特殊字符标题、非首行不剥）。**fix 选在「制造重复的那一层」，而非去改对外部正确的文件。**

> 一句话：同一份内容在「文件态」和「阅读态」的诉求可以不同——标题该留在文件里，重复该消在渲染前。修 bug 先问「谁该为这个症状负责」，别图省事去改一个对其他消费者正确的产物。

## 23. undici 安全补丁：先评暴露面、再升、最后验「external 陷阱」（2026-06-22）

push 后 GitHub 弹出 2 个 Dependabot 漏洞（1 high + 1 moderate），安哥让先分析。一次「告警≠风险」的处置示范。

- **先回答「我们到底受不受影响」，而不是条件反射升级**：两个告警同一个包 `undici@7.27.1`（被 cheerio 与 `@electron/get` 共用），都在 7.28.0 修。逐条核对暴露面——#32 需要用 undici 的 SOCKS5 `ProxyAgent`（我们没有）、#33 需要用 undici 的 HTTP 缓存（我们没有，而且 undici 已 `external` 永不加载）；自有代码零直接引用 undici，只用 `cheerio.load`（纯内存解析，从不走 cheerio 那条 undici-backed 的网络抓取 API）。结论：名义 high/medium，**本项目实际暴露面为零**。**Dependabot 按版本号判定，不按调用路径——所以「分析」这一步是把『被标记』翻译成『真实风险』，别把扫描器的版本匹配当成事实暴露。**
- **升级的理由是「保持归零 + 白送的修复」，不夸大成救火**：暴露面虽零，但照 v0.2.1（§15）把 Dependabot 清零的既定方针 + form-data（`d39b51e`）的 override 先例，加 `overrides: { "undici": "^7.28.0" }`。全局 override 把三处实例（cheerio `^7.24.4`、@electron/get `^7.19.0`、node-gyp `^6.25.0`）统一 deduped 到一份 7.28.0——node-gyp 那份从 6.26.0 被抬到 7.x 是构建期工具，靠下面的 build 验证兜底。**对外说清「这是卫生维护，不是漏洞被利用了」，是这条最该守的诚实（呼应 §21 不夸大抖动疗效）。**
- **transitive bump 后必须重验「undici external 陷阱」**：项目有条硬陷阱——cheerio 依赖的 undici 里 sqlite-cache-store 静态 `require('node:sqlite')`，Electron 内置 Node 没这个模块，一旦被打进 bundle 主进程加载即崩；我们靠 vite `external` 让它惰性永不加载。undici 版本一变，这条必须重测，`npm install` + 单测不够。验证四连：174 单测 + tsc + lint 绿 → mac build 成功 → grep `main.js` 确认 undici 没被打包（`node:sqlite` 0 次、`require("undici")` 仅 1 处惰性引用）→ 真实启动打包后的 `.app` CLI（`auth-status` exit 0、合法 JSON，主进程加载不崩）。**「升级没破坏 external」这种不变量，要用打包产物 + 真机启动证明，不能靠『版本号兼容』推断。**

> 一句话：依赖告警的正解是「先把『被版本匹配标记』还原成『真实调用路径暴露』再决定要不要慌，升级当卫生维护诚实陈述，并对项目特有的不变量（undici external）用打包+真机启动重新验证」——三步都呼应同一条原则：别让工具的判定替代你对自己系统的判断。

## 24. v0.4.0 启动 + M13 存储加固：subagent 驱动开发首秀（2026-06-22）

安哥提了两个深问题——① 文件存储这套机制会不会有问题？② 能不能把文库文章当素材喂给本地 agent 做选题/写作/审阅？这把 v0.4.0 的方向定了下来：**文库供料 agent + 先夯实存储地基**。本节记两件事：v0.4.0 怎么从「问题」收敛成 PRD，以及 M13 第一次用 subagent-driven-development 执行计划的体感。

- **存储隐患是「读出来的」，不是「猜出来的」**：回答「文件存储有没有问题」时没泛泛而谈，而是把 `Library`/`History`/`Subscriptions` 三个索引类的读写真读了一遍，定位到两个真实隐患——① `writeFile` 整文件覆盖**非原子**，崩溃/断电留半截 JSON → 整个索引报废；② 每次写是 `read→改→write` 中间有 `await`，**后台订阅自动下载与前台操作并发会丢更新**（已开自动订阅，这并发是现实，不是理论）。还发现每篇文章目录都有 `meta.json` → `library.json` 本质是**可重建的派生索引**，于是把「损坏只能手删重来」变成「一键 rebuild」。**「存储会不会有问题」这种问题，答案在代码里，不在直觉里。**
- **架构边界先于功能定**：供料这条线最关键的决策不是「导出什么格式」，而是「编排放哪」。brainstorming 里把它逼成单选——wx-kit 只供料、编排活在外部 skill（复用 khazix-writer/hv-analysis），而不是在 app 里造「创作模块」。**守住「下载器」本分，不让它膨胀成「内容工作室」**——这呼应了项目「百宝箱但不预造空模块（YAGNI）」的既定决策。素材用途也写进 PRD §6：选题/研究/启发，不洗稿、强制人在环中。
- **subagent-driven 的价值在「上下文隔离 + 双道闸」**：M13 拆成 8 个 bite-sized 任务，每个派一个**全新 subagent**（带完整 task-brief，不继承主会话历史），完成后**独立 reviewer**（spec 合规 + 代码质量两道验verdict）。模型按任务挑：新文件+完整代码用便宜档（haiku 转写），改既有文件/并发原语用 sonnet 评审。**fresh context 让每个实现者只盯自己那点事，主控（我）只做编排，上下文不被污染。**
- **评审与实现者都逮到了我计划里的真 bug**：Task 4 的实现者发现**我写的并发 append 测试漏了 `now=` 参数**——默认 `Date.now()` 会把日期 1972 的测试事件按保留期裁掉，导致加锁也变不绿。它正确地补上 `now=1000*DAY`，并标 DONE_WITH_CONCERNS 上报。**计划再细也会有洞，双道闸（实现者自审 + 独立评审）就是网。** Task 1 的评审还揪出原子写失败时不清理临时文件（会在库根留孤儿 `.tmp-*`），补了 best-effort 清理。
- **并发丢更新这种隐性 bug，用「并发测试」逼出来**：每个接锁的任务都先写「两个实例并发 add/append」的失败测试——RED 阶段真的只剩一条记录（丢更新复现），加锁后 GREEN 两条都在。**抽象的「竞态」要落成一个会红的测试，才算真的被钉死。**
- **子 agent 跑不了 electron，真机验证留给主会话**：Task 7 的 GUI 接线（IPC+preload+api+设置页按钮）子 agent 能写能过 tsc/lint/单测，但**沙箱解析不了 electron 二进制**，真机验证（`npm run test:e2e` 实机驱动全流程）由主会话做——36 项全过、0 console 错误，证明原子写+写锁垫在底下后实机读写没坏。**知道哪步必须回主会话做，是 subagent 编排的一部分。**

> 一句话：M13 的方法论是**「隐患从代码里读、边界先于功能定、用 fresh-context subagent + 双道闸执行、把竞态钉成会红的测试、电不了的真机验证留主会话」**——第一次 subagent-driven 跑下来，最大的收获是双道闸真能逮出连计划作者都没看见的 bug。

## 25. M14 供料能力：把文库变成 agent 的「素材出口」（2026-06-22）

M14 给 v0.4.0 的主线落地第一块：让选中的文库文章变成 agent 能直接吃的结构化素材。沿用 M13 的 subagent-driven 节奏，4 个任务一气呵成。

- **CLI 与 GUI 共用同一套核心，清单同源**：选料过滤（`selectArticles`）+ 清单组装（`buildManifest`）+ 写盘（`writeMaterialExport`）全在 `material-export.ts` 一处，CLI `library export` 走 stdout、GUI `library:exportMaterial` IPC 写文件，但**清单由同一个 `buildManifest` 出**——不会出现「命令行导的和界面导的字段不一样」这种漂移。这正是「系统承担复杂性」：两个入口、一套真相。
- **只给路径不内联正文**：清单字段固定 `{id,title,account,author,publishTime,sourceUrl,dir,contentPath}`，`contentPath = dir/content.md`。stdout 轻、agent 按需读盘，复用磁盘已有的 `content.md`，不把正文塞进 JSON。**供料的边界感：wx-kit 给「料在哪」，不替 agent 决定「怎么吃」。**
- **「无选料器报错」是防误操作的小闸**：`library export` 不给 `--ids/--since/--account` 也不给 `--all` 时直接 `NO_SELECTOR` 报错退出，而不是默默导全库——避免手一滑把整个文库吐出来。要全库必须显式 `--all`。**危险的默认行为，宁可报错也不猜。**
- **`exports/` 的目录归属在 M13 就埋好了**：GUI 导出写到库内 `exports/<时间戳>.json`，而 M13 的 `rebuildLibrary` 递归扫描早已忽略 `exports/`——所以素材清单不会被误当成文章重建进索引。**跨里程碑的约定提前对齐，比事后打补丁省事。**
- **复用 M13 的原子写**：`writeMaterialExport` 用 `atomicWriteFile` 落盘，导出文件天然也享受「写一半不留半截」。地基夯实后，上层白捡。
- **GUI 按钮镜像既有批量删除**：文库批量条加「导出为素材」，处理器结构、错误提示、`api.reveal` 点击跳转全照 `batchDelete` 的样子——新入口长得像老入口，用户不用重新学。真机验证（`npm run test:e2e` 全流程 + 0 console 错误）由主会话做（子 agent 跑不了 electron）。

> 一句话：M14 的方法论是**「一套核心两个入口（CLI/GUI 同源）、供料只给路径不越界、危险默认宁可报错、跨里程碑约定提前对齐」**——把文库变成素材出口，难的不是导出本身，是守住「下载器只供料」的边界不让它膨胀。

## 26. M15 贯通样例 skill：编排自己的 skill，先读清它们到底是什么（2026-06-22）

v0.4.0 收口：交付一个仓库内的 Claude Code skill `agent/wx-kit-compose`，把 M14 的「素材出口」接到创作流水线——选料 → 选题 → 写作，两个人工检查点。这一节的教训不在编排本身，在「动手编排别人的 skill 前，先读清它们真实是什么」。

- **不套 M13/M14 的执行法，因为交付物变了**：M13/M14 是 TDD 应用代码，配 bite-sized 计划 + subagent 执行。M15 交付的是**一个 skill（markdown 指令）**——没有 red/green 单测、拆不成独立 subagent 任务、验证必须在主会话跑真实素材 + 调别的 skill。硬套 TDD 计划是形式主义。识别「这个里程碑的交付物是什么形态」，再选执行法,而不是惯性套上一个。
- **spec 写「复用 hv-analysis」，读了代码才发现错位**：设计稿当时顺手写「选题候选(复用 hv-analysis)」。真去读 `hv-analysis/SKILL.md` 才看清:它是**重量级单主题联网深研 → 出 PDF 报告**的工具,不是「扫几篇文章提选题方向」的轻量助手。把它整个塞进选题步会变成跑一份 PDF 研究,完全错位。**这是「写文档时想当然、没核对被引用对象真实形态」的又一次复发**(同 §22 fakeid——spec 说有、代码里没有)。于是把发现摆给安哥,他定:选题轻量内联、hv-analysis 仅作旁路。**编排别人的能力前,先把那些能力读穿——description 之外要看它实际吃什么、吐什么。**
- **khazix-writer 已经做了一半,就别重造**:读 `khazix-writer/SKILL.md` 发现它天生吃任意素材、自带 HKR 选题质检、承载笔调。所以本 skill 的写作步**全权委派**给它,选题步只做轻量内联——薄编排层不重写下游能力。**复用的前提是先知道下游到底覆盖了多少。**

## 30. v0.5.2 M20 命令行入口崩溃：验证矩阵的盲区（2026-07-10）

安哥真机 `wx-kit download` 报 `FATAL: Unable to find helper app` + GPU/网络服务连环崩。复盘价值在「为什么 M18 当时没发现」：

- **根因**：M18 建的命令行入口是 **symlink**。macOS 上 Electron 按「自己被调用的路径」定位同 bundle 的 `Frameworks/wx-kit Helper*.app`——经软链调用时到 `~/bin/../Frameworks/` 找,不存在 → GPU/网络/渲染子进程全起不来。
- **为什么漏网**：`--version`/`--help`/`library list` 等**纯主进程命令不需要 Helper**,经软链跑侥幸全过——M18 验证恰好只跑了这类命令。**验证矩阵的维度错了：验了「命令能不能跑」,没验「每类进程形态能不能跑」**。带子进程的命令（download、pdf）才是软链形态的照妖镜。
- **修复形态**：wrapper 脚本（`#!/bin/sh` + `exec "<真实路径>" "$@"`,VS Code `code` 命令同款）。先在真机用临时 wrapper 验证 download+pdf 全通,再动代码——**修复方案先于代码被验证**。
- **旧用户自愈**：`linkStatus` 增加 `legacy` 态（指向 target 的旧 symlink）,ipc `cliLink:status` 遇之静默重建为 wrapper。选这个挂点是因为 `CliLinkPrompt` 每次 GUI 启动都会查一次 status——**老用户开一次 GUI 即修复,零打扰零弹窗**（系统承担复杂性）。renderer 类型保持三态,`legacy` 在 ipc 层消化,不外漏。
- **验证补课**：打包态验证这次经 wrapper 入口跑 `--version` **和** `download --formats md,pdf`（stderr 断言零 Helper/GPU 报错）;真机模拟自愈（放回旧 symlink → 开 GUI → 断言被替换成 wrapper、可执行位、内容逐字节）。README 里「`ln -sf` 建软链」的教程段也是同一坑的传播源,一并改为 wrapper 写法。
- **交互细节**：文案「软链」→「快捷命令」——用户不需要知道实现形态,更不该在形态变化时被术语误导。

> 一句话：M20 的方法论是**「验证要按『进程形态/资源依赖』分维度铺矩阵,别只按命令列表打勾;修复方案先在真机验证再落码;老用户的坏状态让系统在既有触点上静默自愈,别再弹窗;文档里的示例命令也是产品面,同坑要一并清」**。

## 31. v0.5.3 M21 关窗后程序坞无法重开：只做了平台惯例的一半（2026-07-13）

安哥真机报告:dmg 安装后红点关窗,点程序坞图标窗口不再出现,只能强退重开。十行代码的修复,复盘价值在「半个惯例比没有惯例更糟」:

- **根因**:`main.ts` 抄了 mac 惯例的前半句——`window-all-closed` 在 darwin 不退出(应用驻留程序坞)——却没抄后半句:`app.on('activate')` 重建窗口。结果是最差组合:进程活着、图标亮着,但**不存在任何重建窗口的代码路径**,比「关窗即退出」还糟(退出至少能重开)。平台惯例是成对的契约,只实现一半会造出「假死」这种两头不沾的状态。
- **为什么 v0.1.0 潜伏至今**:开发(`npm run dev`)与测试(e2e 整进程启停)都不走「关窗→驻留→激活」路径;只有 dmg 安装后像普通 mac 用户那样红点关窗才踩到。**用户的使用路径和开发者的启停路径是两套,惯例类行为只能在前者暴露**。
- **验证的讲究**:e2e 里 `app.emit('activate')` 只能证明 handler 逻辑对,证不了「点程序坞图标会走到这」。打包态用 `open -a` 对已运行实例发 reopen Apple Event——与点程序坞图标同一事件通道——Playwright 挂 `waitForEvent('window')` 断言重建。**模拟事件验逻辑,真实事件通道验接线,两层都要**。另断言了「窗口存在时 activate 不重复开窗」。
- **踩坑一枚**:验证脚本 stderr 断言把 `IMKCFRunLoopWakeUpReliable`(macOS 输入法框架噪音)当可疑行报错——e2e 里早就过滤它了,新写的脚本忘了。**噪音过滤清单也是可复用资产,散落多处就会重踩**。

> 一句话：M21 的方法论是**「平台惯例是成对契约,实现一半即引入假死态;惯例类行为只在真实用户路径暴露,发版验证要走一遍『安装后像用户那样用』;真实事件通道(open -a reopen)与模拟事件(emit)分层验证」**。

## 32. v0.5.4 M22 订阅检查加固：从用户日志读出三个问题（2026-07-16）

安哥问了一句「检查日志里为什么每天两条、失败的是什么、能不能点开看」——顺着真机日志挖出三个独立缺陷,一版修完:

## 36. v0.8.0 M31+M32 让内容流到该去的地方:分流白名单的隐式契约、跨项目验收、复用前先核实能力边界(2026-07-22)

- **GUI 早有、CLI 缺的逻辑,抽 core 共享而不是复制**:R3 要 CLI 按 publishTime 排序,而 `sortArticles`(含「空 publishTime 恒置末尾」这种边界)早在 `src/renderer/library-view.ts` 里躺着。做法是抽到 `src/core/library-sort.ts`,renderer 改 re-export 保持 import 兼容。**判断依据是分层语义**:排序是领域逻辑归 core,而 `accountsOf`/`groupByAccount` 是视图编排留 renderer。顺带如实标注:`library list` 默认输出从「索引顺序」变成「publishTime 降序」是**轻度 breaking**——原顺序本就不确定、agent 不该依赖,但仍在 PRD 和 skill 文档里显式写明。
- **平台默认行为要主动压制,不是「没做的事就不会发生」**:R5 的 mac CLI 堆 dock 图标,根因是 Electron 在 mac 是 GUI 子系统应用——**进程一启动就在程序坞冒头,哪怕一个窗口都不开**。CLI 分支复用 Electron 进程(PDF 要 BrowserWindow),不显式 `app.dock.hide()` 就必然冒。**跨平台运行时的「什么都不做」不等于「什么都不发生」**;修法一行、放 `whenReady` 前压在图标显示之前,`app.dock` 仅 mac 存在故 win/linux 天然 no-op。
- **产品定位是所有新功能的默认前提,不是可选项**:收 R2 时我把「CLI 也支持 site sync」划进了非目标,安哥当场纠正「同样要支持 CLI,agent 也会用到」。**wx-kit 的双启动模式是产品定位(CLI 输出纯 JSON 就是给 agent 用的),不是 GUI 功能的可选附加**——新功能默认两条通道都要有,除非有理由不给。这条比单个需求更值钱:它是判断后续所有需求边界的默认值。

- **发版收尾:同一个 github,不同通道的连通性完全不同**(2026-07-22 实录)。这次三种访问同时存在:`git push`(ssh)**稳**、`gh release upload` 三个大包(合计 396MB)**全过**、而 `gh release download`(tap 脚本用来算 sha256)**超时挂死**、本地 tap clone 的 `git pull`(https)**连不上**。解法各就各位:sha256 改用本地产物(**刚上传的就是本地文件、尚未重 build,与已发布资产逐字节同源**,gh API 报的三个 size 与本地 `stat` 完全一致可交叉印证);刷新本地 tap 改用 `git fetch git@github.com:...` 走 ssh。**「github 不通」不是一个状态而是四个**,遇卡先换通道再谈兜底。另外这次纠正了 v0.7.0 的一个坏做法:验证已发布 cask 不再用 `--appdir=<临时目录>` 隔离(它会卸掉主安装),改成**直接 `brew upgrade --cask wx-kit` 升主安装**——brew 下载时本就校验 sha256,升级即等于验了 cask + 资产 + 安装路径,还顺手把开发机升到新版,**真实用户路径就是最好的验证路径**。
- **不诚实的验收要主动改回来**:补测试时逐条对账,发现 PRD R5 写着「win/linux 回归测试」而那测试根本不存在(`main.ts` 的启动分流在 app 生命周期里跑,单测构造不出)。改成如实措辞:「无自动化测试,靠代码形态 + mac 真机验证,win/linux 侧属推论未实测」。**验收清单的价值全在可信度**,一条注水就得全表复查——这已经是第二次(v0.7.0 那次是 M30 后批量勾过头),说明**勾选动作本身要逐条回源,不能凭「应该做了」**。

- **v0.8.1 追加:一个「修好了」其实没修好的 bug,以及它暴露的验证方法缺陷**(2026-07-22)。v0.8.0 发出去当天,安哥用正式版跑 `wx-kit -h`,程序坞照旧堆图标——R5 根本没修好。回源实测(`lsappinfo info -only ApplicationType <pid>` 高频采样)拿到状态序列:`NULL → Foreground → UIElement`。三层教训:
  - **API 名字对得上 ≠ 时机对得上**:`app.dock.hide()` 要等 app ready 才生效,而 **AppKit 在 ready 之前就已把进程注册成 `Foreground` 并画了图标**。我当初看 API 语义吻合就用了,没问「它什么时候开始生效」。**平台 API 的生效时机和它的语义同样重要**,尤其当你要压制的是「启动阶段的默认行为」。
  - **图标在 JS 执行前就画了,只能在 plist 层拦**:解法是 `LSUIElement: true`(Launch Services 在进程启动时定为 accessory),GUI 分支 ready 后 `dock.show()` 要回来。**回到第一性原理问「这东西是谁在什么时候画的」,答案就指向唯一可行的层级**——在它之后的任何层都太晚。
  - **最痛的是验证方法**:我当时用跑 2–3 秒的 `download` 测,而且第一次采样前先 `delay 2`,**正好跳过启动瞬间的 `Foreground` 窗口期,只采到稳态的 `UIElement`**,于是报了「已验证通过」。而安哥踩的 `-h` 是最短命的命令,几乎全程在那个窗口期里。**采样验证必须覆盖启动瞬间,不能只看稳态;且该拿最极端的用例测(最短命的命令),不是最顺手的那个**。这条比 bug 本身值钱——同一个陷阱可以出现在任何「短命进程 + 异步生效」的验证里。
  - 连带修正:PRD-v0.8.0 的 R5 验收改成如实记录(标 `[~]` 未达成 + 更正说明),不留一条假的绿勾。**验收表一旦注水,整张表就不可信了**。

> 一句话:v0.8.0 的方法论是**「新增枚举值要同步登记的隐式契约,漏登的症状是挂起不是报错,修完补回归测试钉住;复用现有工具前核实其粒度,同名概念不等于同能力;跨项目产物落进真实目标跑它自己的校验、验完清理不留痕;撞出架构分叉把代价摊开让人决,代价选定即写进 PRD 当已知约束;GUI 有 CLI 缺的逻辑按分层语义抽 core 共享;平台运行时的『没做』不等于『不发生』;产品定位(双通道服务 agent)是新功能的默认前提」**。

## 37. v0.8.2 M34–M36 不让用户猜:错误前提、静默兜底、以及「换数据源」的连带成本(2026-07-26)

三条需求(订阅检查反馈 / 含视频文章 / 更新检查)看着独立,做下来发现共同点是**系统知道但没告诉用户**。而真正值钱的教训几乎全来自「做的过程中发现原本的判断是错的」。

- **收集需求阶段的结论,实现前必须回源复核**。M35 收需求时我抓过页面,写进 PRD 的清晰度排序是 `f10104 > f10102 > f10004 > f10002`——实现前再抓一次,**完全反了**:`f10002` 是 1572×1080/133.5MB(最高清),`f10104` 是 480×328/12.9MB。按 format_id 排序会稳稳选出 480p,**而且没人会发现**(文件确实下来了,只是画质垃圾)。同一次复核还推翻了另一个结论:我说测试文章「确实带 `mp_video_trans_info`」,其实只查了**字段名存在**、没查值——那是个空数组,`mpvideo.qpic.cn` 出现 0 次,根本没视频。**「字段在」不等于「有值」,抓一次真实数据的成本远低于基于错误前提写完一整个里程碑**。
- **分类错了,界面就会长出没意义的选项**。M35 我把视频做成了第六个「下载格式」,安哥试用当场否掉:`cover/md/html/pdf/meta` 是**同一份内容的不同表现形式**,而视频是**内容本身**——图片从来没有「图片」选项,因为没人需要选。链接是普通文章时,那个选项什么都不会发生,纯属噪音。改成「有视频就下」+ 设置里一个开关兜底批量场景。**判断依据是一句话:这东西是同一份内容的另一种呈现,还是内容的一部分?** 答错了,用户每次下载都要面对一个与他无关的勾选框。
- **静默兜底是下一个 bug 的温床**。解析层原本是一串启发式猜测(`#js_content` 非空就当正文用),它**对未知类型永远不报错**:视频消息页的 `#js_content` 是个分享提示壳,第二条规则命中,21.8 万字符的内联 JavaScript 被当正文写进 content.md,一路绿灯到用户手里。改成按 `item_show_type` 显式分发,不认识的类型走兜底**但必须出声**。同时把告警条件收窄:读不到类型而正文正常时不报——**噪音多了告警就会被无视,那等于没做**。
- **换数据源不只是换 URL,是换一整套数据契约**。M36 把列表接口从 `appmsg?type=9`(只给图文素材,370 篇、最新卡在 7-17)换成 `appmsgpublish`(770 篇、全类型、最新 7-25),抓取和订阅一起修好——但我只想着「能拿到全部类型」,没想到**新接口给短链、旧接口给长链**,而文章 id 是从 URL 算的 → 已下载过的文章被重下一遍,安哥试用当场撞上。**换接口时要同时问:它返回的每个字段形态变了吗?下游有谁在依赖旧形态?** 修法是用微信自己的文章主键(`appmsgid`/`itemidx`,列表本来就给)算 id,并让老库的 `mid_idx_sn` 与新的 `mid_idx` 归一匹配,不必迁移 library.json。
- **用户报两个 bug,常常是同一个根因,而且他没报的那一半更严重**。安哥报的是「视频那篇被跳过」和「取不到最新文章」,查下去是同一个接口选错。**但同一条链路上还挂着订阅检查**——订阅号发的文字/视频消息一直在漏检,而检查记录显示「无新文章」,完全看不出来。批量下载少几篇是显性的,订阅静默漏检是隐性的。**顺着根因往上看还有谁在用,比修好报上来的那个症状重要**。
- **两个长得像枚举的字段,不一定是同一个枚举**。`appmsg_type` 与 `item_show_type` 正交:实测 `appmsg_type=10002` 出现在一篇**没有视频**的文字消息上,它根本不表示「有视频」。M35 拿它判视频消息方向就是错的。**同一份数据里两个都叫 type 的字段,先确认它们描述的是不是同一件事。**
- **超时是「按资源体量」的,不是一个常数**。原先只有视频按体积算,页面和图片共用固定 20 秒——而视频消息页实测 2.4MB,20 秒等于要求跑满 120KB/s,慢一点整篇失败(真实抓取偶发过一次)。现在分三档:页面 60 秒、图片 30 秒、视频 `max(60s, 体积÷200KB/s)`。**图片刻意不跟着放宽**:一篇文章的图是串行下的,单张放太松会让「整篇图都拉不动」卡上几十分钟。
- **单测全绿不代表功能是活的**。M35 的视频下载单测全过,第一次真跑就失败——`FETCH_TIMEOUT_MS=20000` 对 133MB 必然超时,而且**失败被我自己写的 catch 静默了**(CLI 报 `ok: true`、videos 目录是空的)。讽刺的是这一版主题恰恰是「不让用户猜」。真实验证的姿势也固化下来了:隔离 userData/库根 + 借真实 `mp-session.json`,把水位调成「恰好一篇算新」,真下真验(`ffprobe` 确认 h264+aac/1572×1080/992.56s、字节数与 `filesize` 逐字节相等)。
- **测试审计要盯「刚出过故障的那条路径」**。补完功能回头审计,发现 `Library.get` 的 canonical 匹配(跨 URL 形态去重的核心)**一条测试都没有**——有人"优化"回字面比较,重复下载会立刻重现而没有任何测试失败。同批还补了队列的主键透传、`downloadArticle` 的「老 id 在库时短链重抓必须在请求页面之前跳过」。**审计的着眼点不是覆盖率数字,是「哪条路径刚坏过、改回错的写法会不会有测试拦住」**。顺带查出队列用对象 rest 把 `title`/`createTime` 也当参数传了下去——**今天无害,但以后给 ArticleRef 加任何字段都会莫名变成下载参数**。

- **M37 追加:「不打扰」不是少写代码,是主动选更弱的提示形态**。更新检查最容易的做法是查到新版就弹窗——一行 `Modal.info` 搞定,且"用户绝对看得见"。但那会在每次启动时打断人,而他多半正想干别的。最后落成:启动延迟 3 秒静默查 → 有新版只在「设置」导航项上点一个 6px 圆点 → 用户自己走进设置页才展开详情。**告知的强度要匹配事情的紧急度**,新版本可用不是紧急事。同批的两个小决定同理:失败一律静默(`checkUpdate` 任何异常都返回 null,断网不该让用户开应用就见错误),以及**只在真发出请求后才记 `lastUpdateCheckAt`**——否则断网一次就要等一天才肯再查。
- **M37 追加:同一句「有新版」对不同渠道的用户意味着完全不同的操作**。brew 装的人该跑 `brew upgrade`,手动下 dmg 的人该重下包——给错了指引比不给更糟。所以识别渠道(查 Caskroom 台账目录而**不** fork `brew list`:打包后的 app 里 PATH 常不全,拿不到 brew 会把 brew 用户误判成手动安装)并给对应动作,brew 渠道那条命令还把我们自己踩过的两个坑(不 `brew update` 读到旧 cask、不 `xattr -cr` 被 Gatekeeper 拦)固化进去,一键复制。**让系统承担「该怎么做」的判断,而不是把选项摊给用户。**
- **M37 追加:自己写二十行 vs 引一个包**。版本比较没引 semver:需要的只是「哪个新」,而 `0.8.10 > 0.8.9` 这一条正是**字符串比较会判反、且要等真发到 0.8.10 才暴露**的坑——单测第一条就钉它。判断标准不是"能不能不引",而是**引入的成本(供应链 + 升级)与自己维护的成本谁更小**;这里明显是后者,并把「预发布后缀只剥离不排序」作为已知简化写在注释里,而不是假装完备。

- **一次自伤事故:写文档的字符被当成命令执行了**(2026-07-26)。给 M37 提交时用 `git commit -m "…"`,message 里为说明技术决策写了带反引号的 `` `brew update` `` / `` `brew list` ``——**双引号里的反引号是命令替换**,于是真跑了 `brew update`(把本机 Homebrew 升到 6.0.12、更新 4 个 tap),`brew list` 的输出还被塞进了 message。所幸 `brew upgrade --cask wx-kit` 那段不在反引号内,没执行,app 没被动;历史未 push,`reset --hard` + `cherry-pick -n` + `-F 文件` 重做即恢复。教训有两层:① **本项目的 commit message 几乎必然含反引号**(全是代码标识),所以规则不是「小心点」而是「一律 `-F 文件`」——把偶发的注意力问题换成结构性的做法;② **我在向用户解释一个命令时,那个命令被执行了**——工具的引号语义不区分「我在说它」和「我在做它」,凡是要引用命令的场景(commit message、文档生成、日志)都得先想清楚这一层。已写进 AGENTS.md 陷阱清单。
- **发版顺带补掉的 flaky**:M37 我写了两条真访问 GitHub 的 CLI 测试,**命令内部 8 秒才超时而 vitest 默认 5 秒判失败**,4 轮里红 1 轮(5009ms)。放宽 vitest 超时只会让套件更慢更飘。删掉联网部分,覆盖移到确定处(注入 fetch 的 core 层 19 条 + 真机跑一次 CLI)。**单测的价值在「快且确定」,拿不确定性换一点真实性是亏的**;要真实就去真机跑,别塞进单测。
- **v0.8.2 发版实录**:流程无新坑(README 亮点段替换不追加、gh 与 push 全程 unset 代理、三个包逐个上传、brew tap 零下载核实约 7 秒)。打包态复验覆盖了本版全部新链路:`--version` 0.8.2、`update --check` 报 `channel: brew`、下含视频的视频消息页(`itemShowType: 5`、视频落盘、content.md 547 字节无 script)——**undici external 与新解析路径在打包态都站得住**。

> 一句话:v0.8.2 的方法论是**「收需求阶段的结论实现前要回源复核(字段存在≠有值);分类错了界面就长出没意义的选项(内容 vs 表现形式);兜底必须出声但要挑准时机,否则噪音让告警失效;换数据源要连带审所有依赖它形态的下游,用户没报的那一半往往更严重;两个都叫 type 的字段先确认是不是一回事;超时按资源体量分档;单测全绿≠功能是活的,真跑一次;测试审计盯刚出过故障的路径而非覆盖率;告知强度要匹配紧急度(不打扰是主动选更弱的形态);同一件事对不同渠道的用户意味着不同操作,让系统承担这个判断」**。

## 38. v0.8.3 M38 打不开的文章不算「下载失败」:一个隔夜就失效的信号,和「静默误滤 vs 明确失败」(2026-07-27)

安哥抓某号最近 3 篇,2 篇失败、报笼统的 `no title parsed`,问「列表接口是否要过滤」。整条链路的价值不在最终代码,而在**为什么最后没按最初的方案做**。

- **信号在,但它隔夜就失效了**。第一天查:打不开的两篇 `checking: 1`,能下的两篇 `checking: 0` —— 证据干净漂亮,方案随即定为「列表阶段过滤」。第二天实现完复现,**那两篇仍然失败**;回查发现它们已经变成 `checking: 0`,而页面照样打不开。`checking` 只标「审核期间」,审核结束后无论通过与否都归零。**一个只观测过一次的字段,不足以支撑一个判定规则**——尤其当它描述的是「正在进行中的状态」时,它的语义天然是会变的。事后看,当时就该问一句:这个字段名是个进行时(checking),它稳定吗?
- **「你确定没有别的方式吗」值得认真对待**。我第一次 diff 时手动排除了一批「固有差异」字段(`cover`/`digest` 也在内),给出「没有别的信号」的结论。安哥追问后重做:把 6 篇的**每个字段(含全部嵌套对象)**做集合对比,不预先排除任何东西,还专门展开了最可能藏标记的 `sent_info` 群发状态块(结果三个字段与能下的完全一致)。结论虽然没变,但**这次是穷尽过的「没有」,而不是筛过一遍的「没找到」**——这两种「没有」的可信度差很远,而我第一次给的是后者却说成了前者。
- **找到了候选信号,但主动没用它**。`line_info.line_count`(打不开的为 0、能下的三四千)看着能用,扫 30 篇里唯一的反例是视频消息——它天然没有正文行数却能正常下载。限定「有正文的类型且 line_count=0」可以做到零误判,但那是**间接的启发式,不是状态标记**,而 M36 刚把启发式换成显式类型分发。真正让我建议放弃的是**代价不对称**:误滤 → 用户**永远看不到**那篇本该能下的文章,而且**静默无声**;不滤 → 多一条明确的失败提示。**当两种错误的代价差这么远时,不该按「命中率」选方案,而该按「错了会怎样」选。**
- **把「做不到」翻译成「做什么」**。既然列表阶段无法预知,就承认它,转而解决用户的真实痛点——安哥原话是「看原因**估计**是违规的」,痛点是**看到失败 + 要猜**。于是:下载阶段认出错误页抛独立的 `ArticleUnavailableError`,汇总把「读者本就打不开」与「真故障」分成两类计数。原案例从 `成功 1 / 失败 2` 变成 **`成功 1 / 真故障 0 / 读者不可见 N`**——**「真故障 0」这一条才是关键**:用户不会再以为是工具坏了。功能没能「消灭失败」,但消灭了**误解**。
- **提示逻辑被安哥当场纠正过一次**。初稿写的是「无论如何都报告跳过 N 篇」,他反问:既然会补齐 N 篇,哪还有「跳过」一说?——对的。那些文章读者根本打不开,**在用户的心智里就不存在**,报「跳过 2 篇」只会让人问「跳过了什么」。正确的标准是**结果是否符合预期**:要 N 篇给了 N 篇就闭嘴,翻到底不够、或日期范围内确实少了才解释。**透明度不等于把内部状态都倒给用户**;倒多了就成了噪音,而噪音会让真正重要的提示也被忽略。
- **认不出就别硬猜**。错误页识别只覆盖三种确定的文案(审核未通过 / 已被作者删除 / 违规下架),认不出的**仍退回原来的笼统说法**。硬把未知失败标成「读者不可见」会掩盖真正的解析故障——**分类的价值在于准,不在于覆盖率**。

> 一句话:v0.8.3 的方法论是**「描述『进行中状态』的字段天然会变,只观测一次不足以立规则;『没找到』与『穷尽后没有』可信度差很远,别把前者说成后者;两种错误代价不对称时按『错了会怎样』选方案,静默误滤远比明确失败糟;做不到就承认,转而消灭误解而非消灭失败;透明度不是把内部状态都倒出来,只在结果不符预期时解释;分类认不出就退回笼统,别硬猜」**。

## 39. v0.8.4 M39–M42 看得见还能挑:五条需求都是「信息已经在手里,只是没交出去」(2026-07-28)

安哥逐条报了五个需求,收齐后才发现它们是同一个形状:**系统手里已经有这个信息,用户或 agent 却用不上、用不准**。没有一条需要新抓数据——工作量全在交互与契约上。这一版的收获多半来自「实现某个需求时,顺着那条路径发现了没人报的旧账」。

- **限流吞掉的不是请求,是结论**(M39)。安哥说 v0.8.2 开着「启动时检查更新」等了一小时没提示。查下来:24 小时内查过就 `return null`,而渲染层只能把 `null` 读成「没有新版」——**「查了没新版」「被限流」「查失败」在调用方眼里长得一模一样**。限流的本意是省请求,却顺手把已知的结论也扣下了。修法是「被限流时返回上次查到的 release」,并且**只存 release、不存 hasUpdate**——按当前版本实时算,升级后提示自动消失,不需要任何清理逻辑。**能靠数据关系自然失效的状态,就别写清理代码。**
- **唯一的定时器长在会消失的地方**。静默检查绑在渲染层挂载后 3 秒,而**关掉窗口那个 effect 就不存在了**;桌面应用常年开着,于是可能几天不查一次。挪到主进程每小时 tick。这里有个容易混的点:**tick 变频繁 ≠ 请求变频繁**——节流仍是「每天最多一次」,tick 只负责「到点问一声」。
- **顺手把编排移进 core,只为让一条难复现的路径可测**(M39)。「断网时静默检查回落到缓存」这条手工几乎没法复现,留在 `ipc.ts` 里就只能靠肉眼保证——而它恰恰是重构中最容易悄悄丢的一条。移进 `update-gate` 后 6 行注入 + 单测钉死。**「这段以后会不会被人改没」是决定放哪一层的合法理由,不亚于纯度。**
- **一个功能让既有缺陷从「无害」变「有害」**(M40)。存新文章一直是整体覆盖——今天用户只能全下或全忽略,pending 从不留存,所以看不出问题。**R4 一旦允许「留几篇回头看」,下次检查发现任何新文章就会把留存的整批冲掉**,而且静默。这类缺陷的特征是:**代码没变、危害却因为新功能而出现**;所以做交互变更时要问「现有实现的哪个前提被我打破了」,而不只是「我要加什么」。
- **同一个 bug 修过一次,却漏了另一个调用点**(M40)。v0.8.2 修过「短链没有文章主键 → 退化成哈希 id → 同一篇被当成两篇重下」,但只修了批量抓取那条路,**订阅下载这条路一直没传主键**,真实文库里已积下 **32/267 篇**哈希 id。教训:修「某类调用的 bug」时,**用 grep 找出这个函数的全部调用点**,别只修手头触发的那个。这次一并发现 GUI 与 CLI 各有一处。
- **失败被静默清出列表,连重试入口都没有**(M40)。下载完无脑清空 pending,失败的那篇也一起没了。改为只移除「成功 / 已在库 / 读者本就打不开(重试无用)」——**「重试有没有用」才是该不该保留的判据**,而不是「成功与否」。v0.8.3 分出的 `unavailable` 在这里第二次派上用场。
- **标签把默认类型的名字用掉了**(M40)。`item_show_type 8`(小绿书)被标成「图文」,而「图文」正是**不标标签**的那个默认类型的名字——于是「标了图文的反而不是普通图文」。安哥问「默认类型是不是不显示」时,真正扎人的是这个自相矛盾。顺带确认了「默认类型不标」这条原则是对的:**标识的价值在于它出现时你就知道这篇不一样**,全标一遍等于全不标。
- **告警产生了,然后消失了**(M40)。M36 立过规矩「未知类型必须进 `warnings`」,但 `warnings` 只经回调汇进下载结果——**只有 CLI 的 JSON 看得到,GUI 模式下产生即消失**。我在 PRD 里还写成了「只写在 meta.json 里给 agent 看」,实现前复核才发现比记的更糟。**「有没有写进去」和「有没有人能看到」是两件事**;定「必须留痕」的规矩时要顺着落点查到底。
- **不解析自然语言,是为了不撒谎**(M41)。`digest --date` 只认 `YYYY-MM-DD`/`today`/`yesterday`,「7月23日」直接报错。理由不是「解析麻烦」,而是**猜错会静默返回另一天的结果,用户根本不会发现**。同理挡掉 `2026-02-30`——`Date` 会静默滚到 3 月,靠回读校验才拦得住。**能把错误变成沉默的输入,一律拒绝。**
- **语义分开比参数分开重要**(M41)。`digest` 与 `check-now` 都在查列表,但一个是「看看那天有什么」、一个是「检查更新」。共用水位会让「查一次历史」把新文章标记吃掉,所以 digest **不推水位**——于是它可以反复查同一天。**两个命令要不要合并,看的是它们对状态做了什么,不是参数像不像。**
- **抄来的知识不会跟着源头变**(M42)。`wx-kit-compose` 落后二十个里程碑而无人察觉,根因是它把 CLI 参数抄进了自己文件里。修法**不是抄得更全**——那只是把同一个 bug 推迟到下次——而是重新划边界:compose 只说「哪一步用哪个能力」,参数与输出契约一律指向 `wx-kit-skill`。**文档漂移大多不是懒,是把可变的东西复制到了不会被一起改的地方。**这条也写进了它自己的避坑清单。
- **同名不同篇再次出现**。真实数据里某号同一天发了两篇标题完全相同、mid 不同的文章,digest 正确给出两条。AGENTS.md 早写过「不能按标题去重」,这次是它第二次自证。

> 一句话:v0.8.4 的方法论是**「限流该省的是请求不是结论;能靠数据关系自然失效的状态别写清理代码;定时器别长在会消失的地方;把难复现的分支移进可测的层是合法的架构理由;新交互会让旧缺陷从无害变有害,先问『我打破了什么前提』;修 bug 要 grep 全部调用点;该不该保留看『重试有没有用』;别让标签占用默认类型的名字;『写进去了』不等于『有人看得到』;能把错误变成沉默的输入一律拒绝;命令合不合并看它对状态做了什么;抄来的知识不会跟着源头变」**。

## 40. v0.8.5 M43 `digest --download`:我把一条链路切在了错误的地方(2026-07-28)

v0.8.4 刚发完,安哥试用 `digest` 后一句话点中要害:「你只提供链接,不就意味着 agent 还得多操作一步」。这一版只有一个需求,但它暴露的是**上一版设计里的一个判断失误**,值得单独记。

- **我把"只读"当成了目的,而它只是手段**。定 `digest` 时我把「看清单」与「取内容」切得很干净,理由写得也漂亮:纯查询、不写库、不推水位、可反复查。这些性质本身都对——**但我用它们说明了"为什么不下载",却没问"用户拿到清单之后会做什么"**。真实用途里这两步几乎总是连着发生,于是那道缝就留给了调用方:它得逐个 `download`,再把「刚下的」(下载输出里有 `dir`)与「本来就有的」(得回查文库)**两种形状合并成一份清单**。这活儿是我省下的,却是它多出来的。**边界划在哪里,要看"谁来缝那道缝",不只看每一侧是否干净。**
- **两种形状的合并是最典型的"该由工具做完"的活**。判断标准我事后总结成一句:**如果调用方必须写代码把我的两个输出对齐,那这两个输出本该是一个。** `dir`/`contentPath` 现在无论来自哪一半都一样,agent 不需要知道"这篇是刚下的还是本来就有的"——那是我的实现细节,不该泄给它。
- **加开关 vs 造新命令**:选了加 `--download`。另造一条命令会让用户每次先想"这次该用哪个",**那等于把我的实现细节推给他去记**。判据是「问题是不是同一个」:问题还是「那天发了什么」,只多一个决定(顺带把正文取来)。
- **"不带 flag 时行为不变"要由结构保证,不是靠自觉**。实现上没给 `subscriptionDigest` 加开关,而是拆成 `subscriptionDigest()` + `fetchMissing()` 两个函数,CLI 里只在 `--download` 时才构造下载依赖。**一个 if 分支的正确性依赖后人不改坏它;两个函数的边界不需要谁记得。**
- **不照搬既有的 latent bug**。`library export` 的 `contentPath` 是无条件 `join(dir,'content.md')`——没选 md 时那个路径指向的文件其实不存在。为"一致"照抄很容易,但**给一个指向不存在文件的路径比不给更糟**:调用方照着读、失败,还得回头猜为什么。所以只在正文真会存在时才给。**「与既有行为一致」不是把已知的坑复制一遍的理由。**
- **计划里的一条依据是错的,读代码才发现**。我在计划里写「复用 `DownloadQueue`,它有串行+随机延迟+频控退避」——实际读它的 `run()`,**它并没有条目间延迟**;文章页是普通 HTTP,频控纪律针对的是列表接口,`crawl` 也只是串行跑。于是直接串行循环。**写计划时凭印象引用某个模块的能力,和凭印象写代码一样不可靠。**
- **v0.8.3 的那个区分第三次派上用场**。真机验证时那两篇同名文章下载失败,`unavailable: true` 正确标出——查下来是**审核未通过后作者重发**。这也顺手解释了此前"同名不同 mid"的成因。**如果 agent 分不清"读者本就打不开"与"网络失败",它会对着死链无限重试**;这个字段的价值不在人看,在自动化不做傻事。
- **文档更新要替换而不是并列**。skill 里原先那条「先 digest 再逐个 download」的范例直接删掉了。留着并列会让 agent 继续用累的那条——**并列等于没更新**。顺带发现 `wx-kit-compose` 与 `commands.md` 也各有一处旧写法(含 M40 已改掉的「图文消息」旧称),一并修。

> 一句话:v0.8.5 的方法论是**「'只读'是手段不是目的,边界划在哪要看谁来缝那道缝;若调用方必须写代码把我的两个输出对齐,它们本该是一个;加开关还是造命令,看问题是不是同一个;'不带 flag 行为不变'要由结构保证而非 if 分支的自觉;与既有行为一致不是复制已知坑的理由;写计划时凭印象引用模块能力和凭印象写代码一样不可靠;文档更新要替换,并列等于没更新」**。

## 41. v0.9.0（原暂归 v0.8.6）M44–M46 请求保护:局部都在排队,全局仍可能一起冲出去(2026-08-02)

这次不是从功能愿望开始,而是从事故边界开始:当前账号/IP已经被频控,因此**验证本身也可能加重惩罚**。
第一条实现规则不是“先发一次看看”,而是冻结所有真实微信访问,只允许 fake transport、本机 fixture、隔离 userData
和能证明零出网的网络闸。M44–M46 阶段 567 项单测、lint、typecheck、离线 GUI e2e 与 macOS 双架构构建通过;
e2e 明确输出微信请求尝试数 `blocked=0`。这些证据只证明客户端治理结构,不证明微信侧已经恢复。

- **每条链路都串行,不等于账号视角没有并发**。旧实现里 crawl 自己 sleep、订阅检查自己 sleep、digest 串行,
  单看每一段都像“做了频控”;但 GUI 搜索、CLI、驻留调度器和多个 DownloadQueue 彼此不知道对方刚发过请求。
  真正的保护对象不是函数,是同一账号/IP看到的总流量。因此所有类别共用一份持久状态、一个下一窗口和一个
  in-flight lease,GUI 与独立 CLI 进程也不能靠各自的内存锁错峰失败。
- **修指纹不是继续补 Header**。扫码窗口走 Chromium,后台 API/文章/媒体却走 Node axios,还在 Windows 上声称
  自己是 macOS Chrome 124。再手写一套 Client Hints 只会制造更多矛盾。正确动作是复用扫码登录所属的
  Chromium Session,让 UA、Cookie Jar、连接和后续 Set-Cookie 自然一致。旧登录文件只在 Jar 为空时恢复;
  已有 Jar 绝不被旧快照覆盖。
- **频控是停机信号,不是“换一个等待时长再撞一次”**。旧 crawl 收到 200013 后按 30/60/90 秒继续请求,
  这在惩罚期里可能延长惩罚。新网关看见 200013、HTTP 429 或高置信验证页就持久熔断,订阅调度不再启动,
  批量队列也立即停在当前项;尚未发送的条目保留为未处理,不会逐篇制造失败记录。
- **状态查询也可能是流量**。GUI 进入按公众号页、CLI `auth-status`、`session import` 原本都会固定搜索“腾讯”。
  这种“为了确认能不能请求而先请求一次”的设计,在频控期尤其荒谬。现在三者只读本地状态并诚实返回
  `valid:null`;真正有效性留到用户明确发起的业务动作中确认。
- **fail closed 要让用户看得懂**。没有状态文件或文件损坏时默认暂停,不是静默放行;设置页持续显示暂停原因、
  上次请求、排队数和最早可执行时间,CLI 提供 `protection status|pause|resume`。恢复只改变本地许可,本身不探测微信。
  代价是升级后第一次要多一次明确恢复,但这比在用户不知情时延长频控更可控。
- **“测试模式”必须能证明自己**。只设置一个环境变量但不观测拦截,仍可能把“请求被拦了”误写成“没有请求”。
  网络闸会对微信域名硬取消并计数,e2e 最后要求计数严格为 0;同时静态边界测试防止未来又从 Node axios
  绕开 Chromium 的 webRequest。两道闸分别守 Chromium 与代码结构,缺一都不完整。
- **离线 e2e 找到了与微信无关、却真实存在的传输缺陷**。统一 binary transport 最初给本机 HTTP fixture 也带
  微信 HTTPS Referer,Chromium 按安全规则拒绝请求,阅读器图片因此不见。修成只对微信资源附微信 Referer。
  这说明冻结真实服务不等于只能做弱验证:fixture 仍能检出协议语义和完整 UI 链路问题。

> 一句话:这一阶段的方法论是**「保护对象是账号看到的总流量,不是某个函数;局部串行不等于全局节制;
> 指纹一致性靠统一真实会话,不靠堆伪造 Header;频控信号应该熔断而不是退避重撞;没有用户意图的状态查询不能偷发请求;
> fail closed 必须同时给出原因与恢复路径;零出网要靠可计数的硬闸证明;冻结真实服务仍可用 fixture 验出完整链路缺陷;
> 离线通过不等于真实兼容性通过」**。

## 42. v0.9.0（原暂归 v0.8.6）M47 会话重置:清 Cookie 不该以删除整个应用状态为代价(2026-08-02)

M47 在旧版本规划中曾于 v0.8.6/v0.8.7 间调整,但一次真实操作暴露了它其实是本轮会话治理的缺口:
为了清旧公众号 Cookie,手工删除了整个 `~/Library/Application Support/wx-kit`,
结果 `settings.json` 也一起消失;应用下次启动只能加载默认值,更新检查又把整套默认配置正式写回磁盘。
用户最先看到的是每日检查时刻和默认下载格式“被还原”,根因却不是设置页,而是退出边界不存在。

- **同一个目录里不等于同一种生命周期**。登录态可以随退出清掉,设置、订阅、请求审计和频控熔断不能。
  “删 userData 最干净”只是在文件系统层面干净,在产品层面是把用户状态混成了一次性耗材。
- **退出登录要清两份真相**。只删 `mp-session.json`,持久分区仍可能自动进入旧账号;只清 Cookie,
  应用又可能继续拿文件里的 token/Cookie 请求。最终只有一个 `clearMpAuthState`,同时清文件、整个
  `persist:mpweixin` 站点存储、连接、HTTP 缓存和认证缓存;登录、重新登录与退出不能各写一套标准。
- **清理失败也需要事务语义,但不是“第一步失败就停”**。每一步独立尝试,尽可能减少残留;
  任何一步失败则整体不报成功,并把失败步骤交给界面重试。这样既不留着本可删掉的凭证,
  也不制造“已退出”的假事实。
- **退出不能成为频控旁路**。登录态与请求保护是两种状态:退出会话不清 `mp-request-state.json`,
  频控熔断仍然保留。否则用户重新登录就能无意中把“必须停手”一起重置掉。
- **首次登录也要走全新会话路径**。本地 session 文件缺失不代表 partition 没残留;所以扫码登录与重新登录
  都先通过全局请求闸,再清旧会话、开窗口。若闸门拒绝,旧会话不动;若用户扫码中途取消,保持未登录。
- **冻结期仍能验证最重要的资产边界**。fake Electron Session 单测覆盖完整清理、幂等和失败聚合;
  网络封锁 e2e 用非默认 `22:03` 与自定义格式作金丝雀,点击真实设置页退出后验证 session 消失、
  设置与保护状态不变、微信请求尝试数仍为 0。真实 A→B 切换诚实留到解冻后。

> 一句话:M47 的方法论是**「同目录不等于同生命周期;退出登录必须同时清应用会话副本与浏览器分区,
> 但绝不能顺手清用户设置和频控状态;清理要尽力完成所有步骤,任何残留都不能谎报成功;
> 没有 session 文件也不等于没有旧浏览器会话;冻结真实服务仍可用非默认设置作金丝雀验证资产边界」**。

## §46 柳暗花明：通过微信读书后端复活订阅 (M52-M53, v0.10.0)

在 M49 黯然退场公众号列表能力仅仅几周后，安哥找到了一篇名为《我找到了公众号文章抓取的最新方法》的文章，提出了借助微信读书网页版拉取公众号历史的新路线。我们随即启动了 v0.10.0 的迭代。

**踩坑与降级决策：**
1. **移动端封杀**：原本打算使用 `i.weread.qq.com/mp/chapters` 的移动端接口，因为它能拉取全部历史并带出阅读/点赞数。但在 Spike 验证时发现，该接口对墨水屏设备 `User-Agent` 施加了极其严厉的风控（返回 HTTP 499 / errcode -2041）。伪造真实手机 UA 又会导致 `accessToken` 的客户端画像不匹配而报登录超时（401 / -2012）。
2. **转向 Plan B (Web 端增量模式)**：由于移动端链路被实质性阻断，我们果断切换至 Web 端接口 `weread.qq.com/api/mp/cover`。它的代价是**只能拿到公众号最新的一篇文章**，历史回补能力彻底丧失。
3. **接口形态的蝴蝶效应**：Web 端接口不返回文章的发布时间（`createTime`）。为了支持 `checkSubscriptions` 的水位（watermark）判断逻辑，我们不得不在列表探测阶段，额外 `fetchHtml` 抓取最新文章的实际页面来提取时间戳，再构建满足内部流转的 `ArticleRef` 契约。
4. **判重兜底**：微信读书拿到的文章链接全是无 `mid/idx` 的短链，在旧逻辑下退化为 `h_` 路径哈希，导致与老库 `mid_idx` 记录无法跨形态去重。我们在 `downloadArticle` 中加入了后置提取：如果请求前没认出主键，拿到 HTML 后立即用正则补出 `mid` 和 `idx`，再查一遍本地库。这个小手术不仅救了微信读书的短链，也把长久以来“手动重复粘贴短链会二次落盘”的老顽疾顺手根治了。

这次重构的架构收益显著：我们没有粗暴地拆除旧代码，而是通过依赖注入把后端的差异全部封在 `wereadListFn` 适配器中。无论是 `check-subscriptions`、`mp-crawl` 还是 `subscription-digest`，都只需接受形如 `(fakeid, sinceTs) => Promise<ArticleRef[]>` 的纯函数，主干编排逻辑一行未改即焕发新生。

## §47 列表封禁终局与「两次反转」：假设越有说服力，越要设计证伪实验（2026-08-27/28）

§46 的 Plan B 交付当晚，真机实测就把它打回原形：扫码登录后批量下载 401。接下来两天
的排查链值得完整留档，因为它示范了「一个看似自洽的技术归因如何被设计出来的判别实验推翻」。

**第一轮（协议层，成立）**：401 的直接原因是登录用了移动端墨水屏协议（`i.weread.qq.com/login`
拿 `accessToken`），业务却调 Web 端 `/api/mp/cover`（要 `wr_skey`）。把 `accessToken`
硬当 `wr_skey` 塞 Cookie 是 Plan B 切换时没被联调验证过的假设——**e2e 全程 mock 恰好把这个假假设一路放行**。
教训：e2e 的 mock 覆盖的是链路接线，覆盖不了鉴权契约；这类契约必须有一次真实联调，哪怕手工。

**第二轮（细节层，成立）**：换 Web 端登录（`getLoginUid/getLoginInfo`）后连修三处真机问题：
`webLoginVid` 是数字不是字符串（`str()` 只认字符串 → 判成「未返回 vid」）；`reviewId`
token 里带 `~` 而 mp 短链认 `_`（加 `~↔_` 自动回退）；登录产生的全量 Cookie 必须落盘
（浏览器扫码的 `Set-Cookie` 全家桶，缺一个指纹 Cookie 都可能被风控）。

**第三轮（归因层，被推翻）**：`web/mp/articles` 恒 `-2041`，一度归因为「网络栈指纹分级」
——因为同一份凭据在系统 Chrome 里能列、在 Electron/undici 里不能，看起来铁证如山。
于是做了「把所有微信读书流量搬进内嵌 Chromium 栈」的大改造。直到用户扫了**真 Chrome 里的
全新登录**（renewal 正常轮换、身份健康），列表**仍然 -2041**——归因被证伪：之前的
「成功」只是账号限制窗口期的巧合叠加。**真相是服务端按账号+端点封禁列表，与客户端无关。**

**方法论沉淀**：
1. **归因强度 ≠ 证据强度**。三方对照实验（A 失败 / B 失败 / C 成功）看起来无懈可击，
   但 A/B/C 之间可能混着未控制的变量（本例：会话新鲜度）。每个关键归因都要问：
   「这个实验里有没有我没注意到的共变量？」
2. **判别实验要打到终点**。三轮 spike 的最后一轮不是「换个客户端」，而是「在最强客户端里
   做最强的登录」——只有把对方理论上的最优解也跑一遍，才能宣布此路不通。
   否则就会在错误归因上继续投工程（Chromium 栈迁移已完成，所幸它本身有独立价值：
   登录与业务的真实浏览器级会话让 `cover` 链路更稳）。
3. **服务端事实 > 客户端努力**。we-mp-rss 文档里那句「恒返回 -2041」其实就是答案，
   当时被「我们能成功一次」的反例带偏了——后来明白那一次本身就是噪声。开源同行的
   结论性记录，权重应高于自己的一次侥幸成功。
4. **边界收缩要收缩得干净**。确认无解后（安哥决策）：GUI 入口删除、CLI 稳定拒绝
   （`MP_BACKEND_UNAVAILABLE`，退出码 2，零网络）、文档五处同步（skill/README/ROADMAP/
   PRD §6/AGENTS.md 陷阱清单）、e2e 断言反转。**留下半吊子入口比没有入口更伤产品信任。**

**同批顺手修的产品问题**（用户实测反馈）：旧版订阅的 base64 fakeid 与新版 `MP_WXS_`
形态导致同名重复行——读取时归一化自动合并，数据无损；订阅行补删除（持久化标记，
历史派生行不复活）；行内「检查」从全局布尔改为按行状态（此前点一行全页转圈，
观感等同触发全量）。三者的共性：**后端切换时数据形态与交互状态的接缝最容易藏问题**。

## §48 v0.10.1 M54：latest-only 接口没有发布时间，就别伪造水位（2026-08-29）

v0.10.0 的 `/api/mp/cover` 只给 `reviewId`、标题和短链，没有发布时间。实现为了复用旧的
`ArticleRef`，把每次读取的同一篇文章赋成“当前时间”，再拿它推进时间水位。结果是确定性的：
下一次检查获得一个更晚的伪时间，同一篇又被报告为新文章；用户点下载后才在文库判重处看到“已存在”。

- **时间字段必须区分来源语义**。给 `ArticleRef` 增加来源稳定身份，`cover` 模式按 `reviewId`
  与 `latestArticleId` 游标比较；发现时间仅用于待处理列表展示与排序，绝不参与新旧判断。首次检查
  没有游标时仍投递当前最新一篇，之后无论提示、下载、忽略或下载失败，成功检查都会推进游标。
- **迁移不能只看新字段有没有**。v0.10.0 已落盘的订阅没有游标；升级后先比当前 cover 短链是否已在
  本地文库，命中即只建立游标、不再提示，避免把用户昨天已下载的文章重报一次。双形态账号合并时也要
  合并游标，否则看似无损的归一会重新制造重复提醒。
- **被证伪的端点不要保留“碰碰运气”探测**。订阅检查曾先试 `/web/mp/articles`，失败才回退 cover。
  列表封禁已是服务端结论，每号多一次请求只会多一次 2.5–5 秒保护等待。生产订阅改为直达 cover；
  不以“未来也许恢复”为由污染日常路径。
- **批量功能应服务于任务，不是复制选择控件**。页面已有单号展开后的文章级选择；再加账号级多选会让
  用户判断“我正在选账号还是文章”。因此只提供一个“下载全部待处理新文章”，按账号顺序复用同一串行
  下载队列；成功、已存在与不可访问项移除，真故障仍留待重试。
- **性能优化先去无效工作，再让等待可解释**。不提高并发、不缩短风控间隔；下载队列把正文、图片、视频、
  导出阶段透传给页面。用户看到的是系统正在做什么，而不是长期停在“0/1”。
- **短链回退必须统一任务身份与本地来源身份**。真实账号再次验收时，cover 待处理保存 `~` token，
  文库保存下载器成功回退后的 `_` token；两者本是同一篇，却让历史 pending 无法清除。现在来源键统一
  `~→_`，检查时会清掉文库已存在的 pending。同时渲染层把自动下载的 `done` 当成删除进度状态，避免
  晚到 IPC 事件在检查 Promise 返回后重新写入 busy 表，造成整页按钮永久禁用。

## §49 M55 设计修订：先确定查询对象，再决定存储和副作用（2026-08-30）

本节记录已确认的设计取舍，不代表 M55 代码已实现。当前进度见 ROADMAP。

最初把“某天发表的订阅文章”设计成独立发现日志，随后用户指出日常已经通过自动检查和自动下载积累文库。
重新梳理后，实际目标是查询本地保存内容的发表日期，而不是永久追踪所有已发现但未下载的文章。
因此撤销 `subscription-articles.json`，日报只取 `library.json`；发现日志在需要保留忽略/未下载历史时才有独立价值。

“过了自动检查时间就直接读库”的建议也不能作为可靠性依据：应用可能没运行，检查可能失败，公众号还可能
在检查之后发文。最终不再推测调度状态，日期只决定筛选范围：不带 `--download` 永远纯本地，包括 today；
只有今天显式加 flag 才刷新最新 cover、下载缺失项并重读文库，非今天的下载请求在联网前拒绝。

真实文库中存在早期 `publishTime` 空值。为保证字段非空而拒绝保存已获取的正文，会把元数据缺失扩大成内容
损失。最终保留正文并告警，日报排除未知日期条目并报告数量，绝不用下载时间补假值；少量存量空值定向修复，
不在启动或查询时隐藏联网，也不新增长期修复命令。M55 的 PRD 与实施计划已据此替换旧方案，CLI 使用说明
待代码实施时同批切换，避免把设计写成已交付能力。

## §50 M55 实施与验收：日报取库，副作用由 flag 决定（2026-08-30）

M55 已将 `subscription digest` 的默认路径改为本地文库查询。`today/yesterday/具体日期` 统一按北京时间，
根据真实 `publishTime` 筛选，不再读取 cover 检查时刻。只有今天的显式 `--download` 构造网关，串行刷新
所选账号的 cover、下载缺失文章，再重读文库；不借用会修改订阅游标与调度的 `check-now`。

- 测试先复现旧行为：无凭据时本地查询失败、非今天的下载未提前拒绝、最新旧文误进今天清单、联网错误被
  吞成“零篇成功”。新 CLI 隔离测试覆盖文件不变、账号筛选、下载后重读、重复短链跳过和错误退出码。
- 独立审查发现单看顶层 catch 不够：图片/视频/封面容错及短链替代重试可能吞掉全局保护信号。现在普通
  资源错误仍可降级，但频控/暂停/鉴权信号必须保留并停止后续请求。cover HTTP 401/403 的映射限定在
  刷新编排，不将普通媒体 403 一律视为登录失效。
- 名称不是公众号身份。新增可选 `accountId` 随下载写入 `meta.json` 和 `library.json`，防止账号改名后
  新入库文章被昵称过滤掉；旧数据依然兼容 URL biz 和昵称，不强制迁移。
- 时间缺失不会阻断正文保存，告警随文章入库；日报排除未知时间，并报告所选账号全库中的未知时间数量。
  两篇早期空值从真实原文核对后定向补齐：2026-06-07 15:23、2026-06-05 14:45。先备份，核对 ID，
  只更新 library/meta 的 `publishTime`，其余字段和正文不变，没有引入长期修复命令。
- 本轮单测 62 文件/519 项、lint、tsc、双架构构建与 GUI fixture e2e 通过；打包 CLI 无凭据查询两个
  已修复历史日期成功。真实 cover 首次刷新下载成功，第二个独立进程却返回 HTTP 401。这条外部链路
  没有用模拟结果覆盖，也未自动反复重试或擅改认证协议；发版前需另行复验连续登录态。

README、wx-kit-skill 三处参考和 compose 路由已同步；已发布版本仍是 v0.10.0，不能把本轮源码行为
描述成现有安装包已经升级。完整验收与残余问题见 M55 计划的执行记录。

## §51 独立进程认证：成功响应也要保存会话演进（2026-08-30）

M55 的真实验收首次独立 CLI 能刷新 cover，第二个新进程却 401。检查传输路径后发现业务请求明确发送
`weread-creds.json` 中的完整 Cookie，而 Chromium 会话在成功响应后可能收到新的 Cookie；旧实现完全没有
把 session jar 的新快照写回文件，于是下个进程继续发送旧 `wr_skey`。这不是“重试一下”能解决的问题，
也不能靠把 401 吞成空结果掩盖。

修复把会话演进收在成功响应后：读取 `persist:weread` jar，Cookie 真变化才以 0600 原子替换写回凭据。
401/403 不覆盖现有凭据，写盘失败不把已成功业务改判失败。传输单测分别钉住成功同步、拒绝不写和写失败容错；
有效扫码后又以两个不共享 Chromium 会话目录的隔离 CLI 进程连续验证成功。当前服务器没有下发新 Cookie，
所以文件哈希未变化；测试证明跨进程使用持久化凭据正常，单测证明发生轮换时会写回。这个规则已写入 AGENTS，
后续不要把 Cookie 当作一次登录后永不变化的静态配置。
