# wx-kit v0.8.4 产品需求文档(迭代 PRD)

> **状态:需求已收齐(R1–R5),2026-07-27 安哥「开工」**。里程碑见 §3,逐条验收见各需求的验收清单。

## 1. 一句话定义

**看得见,还能挑。**

v0.8.2 的主题是「不让用户猜」——把系统知道的告诉用户。这一版往前走一步:
**光告知不够,得让人能据此做选择。**

五条需求是同一个形状:

| 需求 | 系统手里有 | 用户/agent 却 |
|---|---|---|
| R1 | 已经查到了新版本 | 因为限流吞掉结论而毫不知情 |
| R2 | 有 session、能查任意一天 | 没有入口问「昨天各号发了什么」 |
| R3 | CLI 长出了上下游能力 | compose 停在 20 个里程碑前 |
| R4 | 新文章的标题早就存在本地 | 只看得到一个数字,只能全下或全不要 |
| R5 | 知道每篇的消息类型 | 标签把「图片」标成了默认类型的名字 |

**没有一条需要新抓数据**——R4/R5 是零请求的展示层欠账,R1 是把已有结论存下来,
R2 是给已有能力开个入口。这一版的工作量在**交互与契约**,不在采集。

## 2. 需求清单

### R1 · 更新检查在「常开的应用」里几乎不生效(2026-07-27 安哥)

**原始现象**:本机 v0.8.2,设置里「启动时检查更新」是开的,v0.8.3 已发布;
启动应用后**等了至少 1 小时,始终没有新版本提示**。

**核实结论(2026-07-27,读真实状态 + 直接问那个 v0.8.2)**:核心逻辑没问题,**是静默检查这条路径被自己的限流拦住了**。

先排除 core:直接让安哥机器上装的 v0.8.2 自己查——

```json
{"current":"0.8.2","latest":"0.8.3","updateAvailable":true,"channel":"brew", ...}
```

查得到。再看真实状态(`~/Library/Application Support/wx-kit/settings.json`):

| 项 | 值 |
|---|---|
| `updateCheckEnabled` | `true`(开着) |
| `lastUpdateCheckAt` | **2026-07-27 14:29:52** |
| 应用进程启动时刻 | **2026-07-27 13:54:40** |
| v0.8.3 发布时刻 | 2026-07-27 12:03:53 |

启动后 3 秒的那次静默检查,撞上了 M37 写的这段:

```ts
if (opts?.silent) {
  if (s.lastUpdateCheckAt && Date.now() - s.lastUpdateCheckAt < DAY_MS) return null  // 直接返回,根本没查
}
```

24 小时内已有检查记录 → **直接 return null,请求都没发**,前端自然拿不到结果、圆点不出现。

**那条记录很可能是开发期污染的**:做 M37 验证时跑过 `npm run dev`,
**dev 模式与正式安装共享真实 userData**,其启动静默检查照常写 `lastUpdateCheckAt`。
当时只顾着「不碰真实库根」,没意识到 settings 里的这个字段也是共享状态。
(**归因更正**:最初写的是「CLI `update --check` 污染」——回查代码后确认
`src/cli/index.ts` 的 update 命令**根本不写 settings**,污染源是 GUI 那条路径。)

**但根子不是污染,是设计本身有两处缺陷**(即使没被污染,同样会漏):

1. **唯一的检查时机绑在「应用启动」上**。桌面应用常年开着——本机这个进程从 13:54 一直跑到现在。
   若用户昨天启动、今天不重启,**永远不会再查**。
2. **上次的结论没有留存**。就算昨天查到了有新版,那个结果没存下来;
   今天启动被限流跳过后,IPC 返回 `null`,前端无从知道「其实已经有新版了」。
   ——**限流本意是省请求,却把「已知的结论」也一起吞了。**

**方案(两条必须一起,单独任一条都不够)**:

- **缓存上次的结论**:settings 增 `lastKnownLatest`(以及展示所需的少量字段);
  silent 检查被限流跳过时**返回缓存的结论而不是 `null`**——查到过就一直提示,直到升级为止。
  升级后本地版本 ≥ 缓存版本,提示自然消失,无需额外清理。
- **常开也要定期检查**:不能把唯一时机绑在启动上。参考订阅检查的做法(`SubscriptionScheduler` 每分钟 tick、
  到点才真跑),给更新检查一个低频 tick(如每小时一次),**真正的请求频率仍由「每天最多一次」兜底**。
- **顺带**:`lastUpdateCheckAt` 只在「真发出请求」时更新的现有行为保持不变(断网一次不该让人等一天)。

**连带记录(开发纪律)**:`npm run dev` / `npx electron .` **共享真实 userData**,
跑任何会写 settings 的命令都会污染真实状态。以往只注意隔离「库根」(`--out`),
但 `lastUpdateCheckAt`、`cliLinkPrompted`、`librarySort` 这类字段同样是共享的。
验证涉及 settings 时应显式 `--user-data-dir` 隔离。

**临时办法(修复前)**:设置页手动点「检查更新」不受限流影响,能正常看到新版。

**验收(M39 完成,2026-07-27)**:

- [x] 应用常开不重启,新版发布后能在合理时间内自动提示 —— 主进程 `UpdateScheduler` 每小时 tick,
      查到新版广播 `update:available`;**放主进程是因为渲染层的 effect 在关窗后就不跑了**。
- [x] 上次查到有新版、本次启动被限流跳过时**仍然提示** —— 真跑:隔离 userData 造出
      「刚查过 + 缓存里有更高版本」,启动后圆点亮起,`lastUpdateCheckAt` 未变(**证明零请求**)。
- [x] 升级到新版后提示自动消失 —— `infoFromCache` 按当前版本重算 `hasUpdate`,单测钉住
      (缓存 0.8.4 + 当前 0.8.4/0.9.0 → false),**无需任何清理逻辑**。
- [x] 「每天最多一次」的请求节流仍然有效 —— tick 只是「问一声」,节流仍在 `decideUpdateCheck`。
- [x] 关掉「启动时检查更新」后既不发请求也不提示 —— 真跑:同样状态下圆点不亮、时间戳未变。
- [x] 断网行为不回归 —— 静默失败回落缓存且**不写时间戳**(断网一次不该等一天),
      单测覆盖(这条路径手工难复现,故把整段编排移进 core 才钉得住)。
- [x] 手动「检查更新」不受限流影响 —— 真跑:限流状态下点按钮仍发出请求,
      时间戳刷新、缓存写入(`latest 0.8.3` / 3 个资产),设置页显示「已是最新」。
- [x] 复现原场景 —— 即上面第二条,正是安哥那台机器的处境。

### R2 · CLI:查已订阅公众号「某一天」发布了什么(2026-07-27 安哥)

**原始需求**:CLI 增加一个功能,获取已订阅公众号「某一天」发布的文章信息。
「某一天」可以是「昨天」「前天」「2026-07-23」「7月23日」之类的表达;
**不需要文章内容**,返回结果可参考 `library export`。
安哥同时问:**这个需求由 CLI 实现还是 wx-kit-skill 实现更合适?**

**评估结论:两层各做各的,不是二选一。**

| 这件事 | 归谁 | 为什么 |
|---|---|---|
| 「昨天 / 前天 / 7月23日 / 上周三」→ 具体日期 | **skill(agent)** | LLM 最擅长、确定性程序最难做全(中英文、相对表达、跨年…);agent 本来就知道今天几号,换算零成本。CLI 去做要维护一张永远不全的解析表。 |
| 「查订阅号某天发了什么」 | **CLI** | 要 session、遍历订阅号、守频控、解析列表接口——skill 只是说明书没有执行能力,agent 不可能自己调微信接口;且该能力对 GUI 有复用价值。 |

**折中**:CLI 额外只认 `today` / `yesterday` 两个字面量(无歧义、Unix 惯例、省得 agent 算错时区);
更复杂的表达一律由 agent 转成 `YYYY-MM-DD` 再调用。**不在 CLI 里做自然语言解析。**

**现状核实(2026-07-27)**:

- 没有现成命令能干这事:`library list/search` 查的是**已下载**的;`subscription check-now` 是按水位查「有没有新的」;
  `crawl --from/--to` 是单号且**会下载**。
- 但**能力基本齐了**:`listArticles` 已支持 `{from, to}` 日期范围模式,`fetchPage` 已带出 `itemShowType`。
- **成本是真的**:本机 16 个已订阅号 → 查一天 **16 次请求、约 30–60 秒**(串行 + 随机延迟,频控纪律不破)。
  每号通常第一页即覆盖最近几天,所以 16 次是下限。

**细化方案(次要决策为 agent 按项目惯例所定,安哥可推翻)**:

- **命令**:`wx-kit subscription digest --date <YYYY-MM-DD|today|yesterday>`
  (`digest` = 某天的汇总;比 `articles` 更贴切)。
  - `--accounts <fakeid,...>`:只查指定号(**16 个号 30–60 秒,这个口子必须有**)。
  - `--json` 默认;stderr 给逐号进度(否则半分钟无输出像卡死)。
- **输出**(参考 export 但**不照搬**——这些文章还没下载,没有 `dir`/`contentPath`):
  ```jsonc
  { "ok": true, "date": "2026-07-23", "accounts": 16, "count": 7,
    "articles": [{ "account": "...", "title": "...", "publishTime": "...", "url": "...",
                   "itemShowType": 0, "downloaded": true, "id": "mid_idx" }],
    "failures": [{ "nickname": "...", "error": "..." }] }
  ```
  - **`downloaded` 是 export 没有的关键字段**:这篇是否已在库里。它把「发现」与「已有」连起来——
    agent 拿到清单就知道该 `download` 还是直接读本地内容,不必再查一次库。
  - `id` 用 `mid_idx`(与库内一致),agent 可直接拿它对账。
- **不下载、不写库**:纯查询,不碰 library.json,不推进订阅水位(**与 `check-now` 语义分开**——
  这是「看看那天有什么」,不是「检查更新」,不该影响水位)。
- **失败不阻断**:某号查失败(频控/登录态)记进 `failures`,其余照常返回。
**skill 更新是本需求的交付物之一,不是文档附属**(2026-07-27 安哥特别强调):

R2 与其它需求不同——**它本质上是一个给 agent 用的能力,而 skill 是它唯一的入口**。
CLI 命令写好了但 skill 没写,agent 不会凭空知道有 `subscription digest`,这个功能对它**等于不存在**。
所以 skill 条目与 CLI 实现同等重要,**未同步 = 需求未完成**。具体到文件:

| 文件 | 要写什么 |
|---|---|
| `SKILL.md` 速查表 | 加一行命令(agent 先读这里,漏了等于没做);标明**日期由 agent 换算** |
| `references/commands.md` | 完整输出契约(字段逐个说明,重点讲 `downloaded` 与 `id` 怎么用);`--accounts` 与耗时提示;非法日期会报错 |
| `references/recipes.md` | 一条**完整链路**范例:「昨天各号发了什么」→ agent 自己算出日期 → `digest` → 按 `downloaded` 分流(已下的直接读 `content.md`,没下的 `download`)|

**要写进 skill 的三件事**:
① 用户说「昨天 / 前天 / 7月23日」时,**agent 自己换算成 `YYYY-MM-DD`** 再调用(CLI 不解析自然语言,传错会报错);
② `downloaded` 字段决定下一步——已下载的直接读本地 `content.md`,未下载的才 `download`;
③ 订阅号多时耗时较长(16 号约 30–60 秒),可用 `--accounts` 缩小范围。

**验收(草)**:

- [ ] `subscription digest --date 2026-07-23` 返回那天所有已订阅号发布的文章,含 `downloaded` 标记。
- [ ] `--date today` / `--date yesterday` 与显式日期等价(按本机时区计算当天)。
- [ ] 非法日期(`--date 7月23日`)**明确报错并提示格式**,而不是静默当成今天——
      自然语言由 agent 负责换算,CLI 不猜。
- [ ] `--accounts` 只查指定号,请求数与之相符。
- [ ] 某号失败不影响其余号;失败进 `failures`,退出码仍为 0(部分成功)。
- [ ] **不写库、不推进水位**:跑完 `subscription list` 的水位与 `library.json` 均无变化。
- [ ] stderr 有逐号进度;16 号场景不会长时间无输出。
- [ ] **skill 三个文件都已同步**(SKILL.md 速查表 / commands.md 输出契约 / recipes.md 完整链路范例)
      —— 本需求的入口就是 skill,**未同步视为需求未完成**。
- [ ] 用一个「干净」的 agent 会话验证:只读 skill 能否正确完成「看看昨天各号发了什么」
      (含自己换算日期、按 `downloaded` 分流),不靠人补充说明。

### R3 · 让 `agent/wx-kit-compose` 跟上 CLI 的现有能力(2026-07-27 安哥)

**原始需求**:结合现有 wx-kit CLI 的能力,同步更新 `agent/wx-kit-compose`。

**现状核实(2026-07-27)**:

| 项 | 值 |
|---|---|
| 文件 | 单个 `SKILL.md`,80 行 |
| 最后改动 | **2026-06-23**(M15,v0.4.0 时期) |
| 当前版本 | **v0.8.3** —— 中间隔了 v0.5.0 ~ v0.8.3 共 20 多个里程碑 |
| 它认识的 CLI | 只有 `library export` 的四个选料器(`--ids`/`--since`/`--account`/`--all`) |

**关键判断:问题不是「少写了几条命令」,是它错过了完整链路的两端。**

compose 自称「薄编排层」——而编排层的价值恰恰在于**把链路串起来**。
现在链路的上下游都长出了新能力,它却停在中间那一段:

- **上游缺口**:它只能从「**已下载**的文章」开始。而 R2 的 `subscription digest` 正是
  「今天/昨天各号发了什么」——**选题的起点本该在这里**,先看有什么,再决定下什么、写什么。
  现状是用户得先自己下载,compose 才能接手。
- **下游缺口**:它到「初稿」就停了。而 M32 的 `site sync` 能把定稿**直接按 Astro 规范发到个人站点**。
  写完稿还要用户自己去 GUI 点同步,链路断在最后一步。
- **中间也有漏**:`library search`(按关键词找素材)、`library list --sort`(默认发布时间降序,
  「最近的素材」直接取前 N 条)——这些选料手段它都不知道,只会 `export` 那四个选料器。

**顺带发现**:`agent/README.md` 最后改动是 2026-07-19(M28),同样没有 v0.8.x 的能力
(`site sync`/`itemShowType`/`digest` 出现 0 次)。它是两个 skill 的公共入口文档,一并核对。

**细化方案**:

- **补上下游,让链路完整**:
  - 取素材一节增加「从**还没下载**的开始」这条路:`subscription digest`(R2)→ 按 `downloaded` 分流
    → 需要的才 `download` → 再进选料。**这是 compose 最缺的入口**。
  - 定稿后增加可选的下游:`site sync` 发到个人站点(**明确是可选的、且需用户拍板**——
    发布是不可逆的对外动作,不能自动做)。
- **补中间的选料手段**:`library search`(关键词)、`library list --sort/--order`
  (默认发布时间降序,取「最近 N 篇」直接切前 N 条),与既有的 `export` 选料器并列说明。
- **补素材质量信号**(v0.8.x 新增,直接影响选题判断):
  - `itemShowType` —— 素材可能是**视频消息/文字消息**,不是每篇都有长正文;
    视频消息的「正文」只是一段描述,当素材的价值与图文完全不同,选题时要知道。
  - `warnings` —— 「下到了但可能不对」的唯一信号(未识别类型、正文疑似脚本),
    读素材前该扫一眼,别拿一篇解析坏了的当素材。
- **结构**:80 行的单文件已经够紧;若补完超过 ~150 行,按 wx-kit-skill 的惯例拆
  `references/`(SKILL.md 留流程与检查点,细节外置),**别把编排流程淹没在命令清单里**。
- **不动的部分**(它现在是对的,勿改坏):两个 🛑 检查点、「选题轻量内联不调 hv-analysis」、
  「写作全权交 khazix-writer」、「只经 CLI/导出文件取数,绝不读 library.json 或 import 代码」这条契约边界。
- **`agent/README.md` 一并核对**:两个 skill 的公共入口,CLI 路径与能力概述要跟上。

**依赖**:R3 的「上游」部分依赖 R2 的 `subscription digest`,**排期上 R3 应在 R2 之后**。

**验收(草)**:

- [ ] 取素材一节含「从未下载的开始」链路:`digest` → 按 `downloaded` 分流 → 按需 `download` → 选料。
- [ ] 选料手段补齐 `library search` 与 `list --sort/--order`,与 `export` 选料器并列。
- [ ] 说明 `itemShowType` 与 `warnings` 对选题的意义(不是罗列字段,要说**它影响你怎么判断这篇素材**)。
- [ ] 定稿后的 `site sync` 作为**可选下游**写入,并明确「发布是对外动作,须用户拍板」。
- [ ] 两个检查点、khazix-writer 委派、契约边界四条**原样保留**,不被新内容冲淡。
- [ ] `agent/README.md` 与现有 CLI 一致(命令清单、路径、能力概述)。
- [ ] **干净 agent 会话验证**:只读 compose(+ wx-kit-skill)能否完成
      「看看昨天各号发了什么 → 挑两篇 → 写一篇」的完整链路,并在两个检查点正确停下。

### R4 · 订阅检查要能看见「是哪几篇」,并可挑着下载/忽略(2026-07-27 安哥)

**原始需求**:订阅页面中,不管手动检查还是自动检查,目前每个公众号只显示有几篇新文章,
无法查看具体是哪几篇。希望能看到文章标题,除了「下载全部」,还要能**有选择地下载与忽略**。

**现状核实(2026-07-27,读代码)**:

| 事实 | 位置 |
|---|---|
| 新文章的**完整信息早就存在本地了** | `subscriptions.json` 的 `newRefs: ArticleRef[]` |
| 每条含 `title` / `url` / `createTime` / `itemShowType` / `appmsgid` / `itemidx` | `src/core/mp-types.ts:19` |
| UI **只用了 `.length`**(三处:标题旁的红标、按钮文案、侧栏计数) | `Subscriptions.tsx:213/216/231`、`MainLayout.tsx:20` |
| CLI 的 `subscription list` **已经把 `newRefs` 整个吐出来了** | `src/cli/index.ts:335` |

**所以这不是「要多抓一次数据」,是已有的数据没给用户看。零额外请求、零频控成本。**
反过来说这也是个信号:数据层做对了、展示层欠账——agent 能看见的东西,人反而看不见。

**水位不用重新设计(这点先确认清楚,否则方案会跑偏)**:
检查时 `updateWatermark(r.fakeid, r.latest)` 在存 `newRefs` **之前**就执行了
(`subscription-check.ts:83`),水位已越过全部新文章。因此:

- `newRefs` 是这批文章的**唯一台账**,不是「待推进水位的缓冲区」。
- 部分下载 / 部分忽略 / 部分留着不动,**都不影响水位**,也不会被下次检查重复发现。
- 附带发现:`ipc.ts:331` 的 `dismissNew` 里那次 `updateWatermark` 实际是 no-op(水位早已 ≥ 所有 newRefs)。
  留着无害,但别把它当成「忽略靠推水位实现」——不是。

**⚠️ 一个被 R4 放大的既有缺陷(必须一起修,否则新功能是有害的)**:

`setNewRefs` 是**整体覆盖**(`subscriptions.ts:114`)。今天用户对新文章只有「全下」或「全忽略」两种处理,
`newRefs` 基本不会长期留存,所以看不出问题。**R4 一旦让用户「挑两篇下,剩下的留着回头看」,
留着的那几篇会在下一次检查发现任何新文章时被整批冲掉**(`subscription-check.ts:101` 覆盖写入)
——静默丢失,用户只会觉得「刚才明明有 5 篇,现在怎么只剩 2 篇」。
**改为合并**:新发现的 refs 追加到现有 pending,按 `mid_idx` 去重(判重依据与文库一致,见 AGENTS.md)。

**适用范围**:「发现新文章时」设为**提示**才有 pending 可挑;设为**自动下载**时 `newRefs` 从不落地
(`subscription-check.ts:98` 下完即清)。R4 是给「提示」模式的。这是既有设计,不改
——但 UI 上不该让人困惑「为什么我这里从来没有列表」,策略常驻显示已能解释(v0.8.2 R1 已做)。

**细化方案(交互为主,次要决策为 agent 按项目惯例所定,安哥可推翻)**:

- **渐进式展示,不占常态版面**:行内保持现在的样子(`N 新` 标签),新增可展开区
  ——收起时和今天一模一样,展开才列标题。**不能让 16 个号的列表一上来就铺开几十行。**
- **每篇一行**:标题 + 发布时间 + 类型标识(`itemShowType`:视频消息/文字消息/小绿书,
  与文库列表同一套标识,**不下载也能看出这篇是不是长文**——这正是「要不要下」的判断依据)。
- **默认全选**:最常见的路径仍是一键下全部,按钮随勾选变化(「下载所选(3)」)。
  **默认不选会让「全下」从一次点击变成 N+1 次**,是倒退。
- **标题可点开原文**:光看标题常常判断不了值不值得下。点击用外部浏览器打开微信原文
  (复用既有 `openExternal`),看完再决定。**这是「有选择」能成立的前提**,不是附加功能。
- **两个动作**:`下载所选` / `忽略所选`。忽略即从 pending 移除(水位已过,不会再出现),
  **忽略前不额外确认**——但要能看清忽略的是哪几篇(已勾选可见),这比弹窗更有效。
- **IPC 向后兼容**:`subscriptions:downloadNew(fakeid, ids?)` / `dismissNew(fakeid, ids?)`,
  省略 `ids` 即全部(现有调用方与 e2e 不动)。
- **下载进度沿用现有那套**(v0.8.2 R1 的行内进度条),不新造机制;部分下载时 `total` 为所选篇数。
- **CLI 不动**:`subscription list` 已经输出 `newRefs` 全量,agent 侧无缺口。

**验收(草)**:

- [ ] 订阅行可展开,列出该号全部待处理新文章的**标题 + 发布时间 + 类型标识**;收起时版面与现在一致。
- [ ] 手动检查与自动检查(提示模式)得到的列表**一致**——两条路径都存 `newRefs`,不能只有一条能看。
- [ ] 勾选部分文章 → `下载所选` 只下这几篇;**未选中的仍留在待处理列表里**,不被清空。
- [ ] 勾选部分文章 → `忽略所选` 只移除这几篇;其余仍在。
- [ ] 默认全选;不改选直接点即等价于今天的「下载 N 篇新文章」。
- [ ] 点标题在外部浏览器打开原文(不在应用内跳转、不影响待处理状态)。
- [ ] **留存不丢**(核心回归):留 2 篇不处理 → 再检查一次并发现 1 篇新的 →
      列表应为 **3 篇**,而不是被覆盖成 1 篇。
- [ ] 部分下载/忽略后**水位不回退、不重复发现**:再检查一次不得把已处理的文章重新报为新文章。
- [ ] 侧栏与行内的「N 新」计数在部分处理后正确减少。
- [ ] 自动下载模式行为不回归(下完即清,不出现空的展开区)。
- [ ] e2e 覆盖:展开 → 取消勾选一篇 → 下载所选 → 剩余篇数正确。

### R5 · 文库卡片的类型标识:默认类型不标是对的,但标签本身有 bug(2026-07-27 安哥)

**原始提问**:文章类型标识,当前默认的主要类型是不是不会在文库卡片中显示,只会显示「视频」「文字」?

**核实结论:属实,且是 M36 有意为之——但同一行里藏着一个真 bug。**

```ts
// ArticleCard.tsx:22  注释:「只标非普通图文——0/11 是默认形态,标了等于没标」
function kindLabel(t?: number): string {
  return t === 5 ? '视频' : t === 10 ? '文字' : t === 8 ? '图文' : ''
}
```

**「不标默认类型」这条保留**:文库里绝大多数是普通图文,全标一遍等于全不标,
标识的价值恰恰在于**它出现时你就知道这篇不一样**。这与「渐进式展示」是同一条原则。

**但有三个真问题(前两个必修)**:

1. **`t === 8` 标成「图文」是错的,而且是最坏的一种错**。8 是**小绿书(图片消息)**,
   「图文」偏偏是**不标标签的那个默认类型的名字**——于是语义自相矛盾:
   标了「图文」的不是普通图文,普通图文什么都不标。安哥的困惑很可能就是被这个撞出来的。
   **改为「图片」**(与 `message-kind.ts` 的 `picture` 一致;「小绿书」是微信黑话,不进 UI 文案)。
2. **未知类型(开放集合)不标,而它恰恰最该标**。`kindLabel` 对未知 `t` 返回 `''`,
   与「普通图文」在卡片上**完全无法区分**。但未知类型走的是兜底解析、`warnings` 里有话说
   ——这是 M36 立下的规矩(「未知类型必须走兜底 + 进 warnings」),**结果 warnings 在 GUI 里一个字都没露出**,
   只写在 `meta.json` 里给 agent 看。「下到了但可能不对」的信号,人看不见。
   → 未知类型给一个**警示态**标识(如 `⚠ 未知类型`),并让 `warnings` 在卡片/阅读器可见(hover 或详情)。
3. **`11 发布通告` 归入默认不标**:它在 `message-kind.ts` 里映射成 `article`,内容形态确实接近图文,
   现状可接受。**不改**,但记在这里免得下次又被当成遗漏重查一遍。

**顺带对齐(避免两处漂移)**:R4 要在订阅待处理列表里显示类型标识,
**必须与文库卡片共用同一份映射**——现在这份映射是 `ArticleCard.tsx` 里的私有函数,
第二个调用方出现前应上提到 `src/core/message-kind.ts`(那里已有 `MessageKind`,缺的只是展示文案)。
**两处各写一份必然漂**(AGENTS.md 已有同类教训:GUI 与 CLI 各判一次必然漂)。

**验收(草)**:

- [ ] 普通图文(0)与发布通告(11)**仍不显示类型标识**(现状,不得回归)。
- [ ] `itemShowType === 8` 显示「图片」,不再显示与默认类型同名的「图文」。
- [ ] 未识别的 `itemShowType` 显示可辨的警示态标识,与「无标识 = 普通图文」不再混淆。
- [ ] 解析产生的 `warnings` 在 GUI 可见(不必显眼,但**必须能找到**),不再只存在于 meta.json。
- [ ] 类型 → 文案的映射**只有一份**(在 `core/message-kind.ts`),文库卡片与订阅列表(R4)共用。
- [ ] 已下载的老文章不需要重新下载即可正确显示(标识只读 `meta.itemShowType`,无迁移)。

## 4. 非目标

- **不做静默自动升级**——延续 v0.8.2 R3 的结论(adhoc 签名下 Squirrel 必败、与 brew 版本账本打架)。
  R1 只修「该提示却没提示」,不改「不替换二进制」这条。
- **不做 GUI 版的 digest**(R2 只上 CLI)。先验证 agent 场景是否真被用起来;
  GUI 里「某天发了什么」与订阅检查在概念上容易打架(一个是浏览、一个是水位),想清楚再说。
- **不在 CLI 里做自然语言日期解析**——只认 `YYYY-MM-DD` / `today` / `yesterday`,
  「昨天/前天/7月23日」由 agent 换算(R2 已定,理由见该节)。
- **忽略之后不做「回收站」**。水位已越过,恢复要重新翻列表,成本与价值不匹配;
  真要找回,`crawl --from/--to` 或 `digest` 都能重新拿到。
- **不重排文库卡片的信息架构**。R5 只修标签文案 + 补未知类型的警示态 + 让 warnings 找得到,
  不动卡片布局、不加筛选维度。
- **订阅待处理不做跨号汇总视图**。R4 只在各号行内展开;
  「所有号最近有什么」是 `digest`(R2)的事,不在订阅页重造一个。
- **不做已下载文章的类型回填**。标识只读 `meta.itemShowType`,老文章没有该字段就不标,
  不迁移 library.json、不重新下载。
