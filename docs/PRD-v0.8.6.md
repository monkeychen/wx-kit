# wx-kit v0.8.6 产品需求文档(紧急频控修复)

> **状态:范围已确认,待实现**(2026-08-02)。
> 本版本插队到原 v0.8.6 之前;原 v0.8.6 的 R1–R5 顺延为 v0.8.7。
> **真实微信访问冻结**:安哥解除冻结前,开发、测试、打包验证均不得向微信域名发起请求。

## 1. 一句话定义

把所有微信请求收口到同一个、可暂停、可观测、跨入口生效的请求网关,
消除当前明显矛盾的客户端指纹和隐藏请求,一旦出现频控信号立即全局停手,不再用重试延长惩罚。

## 2. 背景与目标边界

安哥当前使用的 wx-kit 已被微信频控。继续用真实账号/IP做“修好了吗”的探测,
本身就可能加重或延长惩罚,所以本版本必须先在**零微信访问**条件下完成。

原始目标是“让每次请求都更像人工操作,而没有自动化痕迹”。这里必须把边界说实:

- **能做到**:消除 wx-kit 自己制造的明显矛盾(错误 UA、Node 与浏览器会话割裂、固定隐藏探测、
  多入口各自限流、命中频控后继续重试),让请求来自同一真实 Chromium 会话并服从人类操作节奏。
- **不能承诺**:“完全没有自动化痕迹”或“以后一定不被频控”。微信还可能综合账号、IP、设备、
  会话历史、访问规模和服务端规则判断;这些不由客户端单方面控制。
- **不采用**:代理/IP 轮换、账号轮换、验证码绕过、伪造设备农场、对抗性隐身脚本。
  本版本做的是请求一致性和节制,不是绕过平台风控。

## 3. 静态审计结论(2026-08-02,全程未访问微信)

### 3.1 请求指纹存在明显自相矛盾

1. 微信后台接口和文章/媒体下载都走 `axios`,即 Node HTTP/TLS 网络栈;
   扫码登录窗口却走 Electron Chromium 网络栈。**同一登录态前后像两种客户端**。
2. 两套请求都写死
   `Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) ... Chrome/124.0`:
   Windows 包也声称自己是 macOS,而当前 Electron 内置 Chromium 版本也不是 Chrome 124。
3. 后台接口只带固定 `User-Agent`、固定 `Referer` 和手工拼接的 `Cookie`;
   文章页与二进制资源又是另一组固定头。它们不共享登录窗口的 Cookie Jar、缓存、连接和会话演进。
4. `mp-session.json` 只保存 Cookie 的 name/value 快照。服务端后续更新 Cookie 时,
   手工 `Cookie` 字符串不会随 Chromium 持久分区自然演进,会话文件与真实浏览器分区可能逐渐分叉。

结论:继续“多补几个浏览器 Header”只会制造更多互相打架的字段。
正确方向是**复用登录窗口所属 Chromium Session 的网络栈和 Cookie Jar**,不再自己扮演浏览器。

### 3.2 当前不是全局频控,只是局部 sleep

现有延迟散落在各流程,彼此不知道对方正在请求:

| 路径 | 当前行为 | 风险 |
|---|---|---|
| GUI 打开“按公众号下载”页 | 自动用固定关键词“腾讯”调用一次 `searchbiz` 验证登录态 | 用户没操作也产生后台请求;重复进入页面会重复留下同一模式 |
| CLI `auth-status` | 同样搜索“腾讯” | 状态查询本身变成真实流量 |
| `session import` | 导入后立即搜索“腾讯” | 导入动作隐含一次真实请求 |
| 公众号搜索 | 每次点击直接请求,无全局间隔、无去重 | 可与订阅检查/抓取重叠 |
| 批量抓取列表 | 仅同一账号翻页间隔 1–3 秒 | 不知道其它入口刚请求过 |
| 批量抓取命中 200013 | 30/60/90 秒后继续重试 | 已被限制时追加请求,可能延长惩罚 |
| 订阅自动/手动检查 | 本流程内逐号 3–8 秒并打乱顺序 | 只保护自己;挡不住搜索、crawl、digest、CLI 并发 |
| `subscription digest` | 账号串行,但账号首屏之间**没有随机间隔** | 每号只取一页时可连续快速请求多个账号 |
| URL/订阅/digest 下载文章 | 多个 `DownloadQueue` 可各自启动,大多没有条目间全局门控 | 文章页与图片/视频请求可和后台接口同时发生 |
| GUI 与 CLI 同时运行 | 各进程各自限流 | 单进程内看似串行,账号/IP视角仍可能并发 |

另外,macOS 关闭 GUI 窗口后应用仍驻留,订阅调度器继续存在;“关了窗口”不等于停止微信访问。

## 4. 需求清单

### R1 · 全局请求网关:所有微信流量只能走一条出口

- 所有微信相关生产请求必须经过统一网关,覆盖:
  - `searchbiz`、`appmsgpublish` 等公众号后台接口;
  - 文章 HTML;
  - 微信图片、封面、视频等资源;
  - GUI、CLI、订阅自动检查、手动检查、digest、登录态显式验证。
- 禁止业务代码直接调用 `axios` / Node `fetch` 访问微信域名。
- 网关按请求类别治理,但共享一个全局状态:后台接口严格串行;
  文章及其资源允许符合一次页面阅读的受控资源阶段,不能与另一个后台动作无约束并发。
- GUI 与 CLI 必须共享持久化的 `lastRequestAt`、`cooldownUntil`、暂停原因和跨进程互斥,
  不能靠重启应用或另开 CLI 绕过等待。
- 同一用户动作产生的重复请求要合并或复用结果;不为“确认状态”重复访问微信。

### R2 · 请求一致性:复用 Chromium Session,不手工伪装浏览器

- 微信请求改走 Electron Session/Chromium 网络栈,与扫码登录使用同一个专用持久分区。
- Cookie 以 Chromium Cookie Jar 为运行时唯一真相;扫码、导入和请求后的 Cookie 更新都写回同一分区。
  `mp-session.json` 只保留必要元数据/迁移能力,不再让一份静态 Cookie 字符串长期脱离浏览器分区运行。
- User-Agent、平台信息、连接复用及浏览器自动生成的协议字段必须彼此一致;
  删除“所有平台固定伪装成 macOS Chrome 124”的实现。
- 不靠手写一长串 `sec-ch-*` / `sec-fetch-*` Header 伪装 Chrome;
  这些字段应由所用 Chromium 栈自然生成,避免 UA、Client Hints 与 TLS 特征互相矛盾。
- 后台接口、文章页与媒体资源保留各自合理的页面语义,但共用同一会话和治理入口。

### R3 · 人类操作节奏:动作级随机等待,而不是散落的固定 sleep

- 频控策略在一个可单测的纯逻辑模块中定义,调用方不得自行 `sleep` 后直发请求。
- 后台操作采用保守的随机思考间隔,连续翻页、跨账号、搜索、订阅检查分别建模;
  不使用固定整秒周期,也不在每次启动时执行同一探测。
- 随机数、时钟和等待均可注入,测试使用假时钟和确定性随机源,不真的等待、更不真的联网。
- 队列等待必须对用户可见且可取消;取消后排队请求不得继续发出。
- 具体默认间隔在实现计划中以“保守优先”给出,但不得宣称它是微信官方安全阈值;
  设置页不提供鼓励用户调快的“极速模式”。

### R4 · 全局熔断:看见频控立即停,不自动试探恢复

- 任一入口收到 `200013`、HTTP 429、明确的频控/验证页或其它高置信风险信号后:
  1. 当前请求返回结构化频控错误;
  2. 立即打开全局熔断,停止自动调度并拒绝后续微信请求;
  3. 清空尚未发出的队列,保留业务任务进度,不把未执行项伪装成失败或成功;
  4. 持久化熔断状态,应用重启、GUI/CLI 切换后仍然有效。
- **删除 `crawlAccount` 命中 200013 后的 30/60/90 秒自动重试**。
- 熔断后不做“探测是否恢复”的定时请求。恢复必须由用户明确操作;
  首次恢复请求也经过完整门控,失败立即重新熔断。
- 普通网络超时与明确频控分开:网络故障可以留待用户稍后重试,但不能触发紧密自动重试风暴。

### R5 · 消灭隐藏请求:没有用户意图就不访问微信

- GUI `mp:authStatus` 改为本地状态检查,打开页面不再偷偷搜索“腾讯”。
- CLI `auth-status` 默认只报告本地状态和上次已知结论;若以后保留真探测,
  必须是显式参数/动作,并经过全局网关。
- `session import` 默认只导入并报告“有效性未知”,不立即发请求;
  显式验证也必须受全局冻结/熔断/间隔约束。
- 订阅调度器启动补检、建立订阅水位、手动检查、digest 等所有隐含出网点都要在 UI/CLI 说明中可发现。
- 修复 digest 跨账号首屏无等待;删除“串行就等于安全”的错误假设。

### R6 · 用户看得见系统为什么没有请求

- 设置页新增“微信请求保护”状态,至少显示:
  - 正常 / 排队等待 / 用户暂停 / 频控熔断;
  - 暂停原因、上次微信请求时间、最早可执行时间;
  - 当前是否存在排队任务。
- 频控时提示“已停止所有微信访问,不会自动重试”,而不是只显示一次接口错误。
- CLI 使用稳定错误码区分 `MP_GOVERNOR_PAUSED`、`MP_RATE_LIMITED`、`MP_COOLDOWN`、
  `MP_AUTH_REQUIRED`,并给出下一步;stdout 继续保持纯 JSON。
- 请求审计日志只记录时间、入口、请求类别、决策(放行/等待/拒绝)和脱敏 endpoint;
  **不得记录 token、Cookie、完整查询参数或文章鉴权 URL**。

### R7 · 真实微信访问冻结与离线验证

从 2026-08-02 起,直到安哥明确解除:

- 禁止运行任何会访问微信的真实登录、`auth-status` 真探测、search、crawl、订阅检查、digest、
  文章/图片/视频下载及 live e2e。
- 单测只用注入 transport、fixture 响应、假时钟和确定性随机源。
- 增加“网络封锁测试模式”:测试/离线 e2e 中一旦尝试访问微信域名立即失败,
  让“我们以为没联网”变成机器可验证的约束。
- 打包后启动验证只能使用隔离 `userData` + 网络封锁模式;不得加载安哥当前真实 session。
- 静态检查保证生产代码访问微信域名只能出现在统一网关/endpoint 定义和 fixture 中,
  不得重新出现旁路 `axios.get()`。
- 在冻结期完成的验证只能证明“网关逻辑、请求一致性结构和零意外出网”;
  **不能写成“已通过真实微信验证”或“频控已解除”**。
- 解冻后的首次 live smoke 另行由安哥授权,严格限定为一个人工触发的小流量场景、零自动重试;
  未获授权不执行。

## 5. 里程碑拆分

- **M44 · 全局请求治理与熔断**:统一决策模块、持久状态、跨入口/跨进程互斥、
  200013 零重试、所有排队与取消语义。
- **M45 · Chromium 会话请求栈**:后台 API/文章/媒体统一改走专用 Electron Session,
  Cookie Jar 单一真相,移除固定 Mac Chrome 124 和生产旁路 axios。
- **M46 · 隐藏请求清理、可观测性与离线验收**:auth-status/import/scheduler/digest 行为收口,
  设置页/CLI 状态反馈,网络封锁测试模式与全套 fixture 验证。

详细任务见 `docs/plans/2026-08-02-m44-m46-request-governance.md`。

## 6. 验收契约

- [ ] 代码静态扫描确认:所有微信请求只能通过统一网关;生产路径无微信域名旁路 axios/Node fetch。
- [ ] Windows/macOS 不再统一声称自己是 macOS Chrome 124;请求身份与所用 Chromium Session 一致。
- [ ] GUI/CLI/订阅/digest/crawl 同时请求时,全局只按一个队列和一个持久状态决策。
- [ ] 进入按公众号下载页、执行默认 `auth-status`、导入 session 均为零微信请求。
- [ ] digest 连续多个账号的首屏请求也经过全局随机间隔。
- [ ] 模拟 200013 后没有第二次请求;所有入口立即被熔断,重启后仍保持暂停。
- [ ] 模拟取消排队任务后,transport 调用次数不增加。
- [ ] UI/CLI 能解释“为什么没发请求、何时可继续、是否已经全局暂停”。
- [ ] 日志不含 token、Cookie、完整敏感 URL。
- [ ] `npm test`、`npm run lint`、`npm run typecheck`、离线 e2e、build 通过;
      全流程由网络封锁证明没有访问微信。
- [ ] 发布说明明确标注:冻结期未做真实微信联调;不声称能够绕过或保证不触发微信风控。

## 7. 非目标

- 不在本版本实现 v0.8.7 已收集的链接交互、安全依赖升级、README 重做、
  pending 失败可见和重新登录/退出登录;除非它们是本修复的直接依赖。
- 不通过增加并发、缩短间隔或批量账号/IP轮换追求下载速度。
- 不猜测微信频控惩罚时长,不提供自动“到点试一下”的探针。
- 不把 fixture/e2e 通过包装成真实账号、真实网络已验证。
