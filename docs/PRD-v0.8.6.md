### R1 · 可点的东西要看起来可点:链接缺手型光标(2026-07-28 安哥)

**原始现象**:订阅页「发现新文章时:仅提示 ⚙ … 📄 打开检查日志」这一行里的两个链接
(打开设置、打开检查日志),**鼠标移上去没有变成手型**。

**核实结论(2026-07-28 读代码 + 查 antd 实现)**:属实,但根因不在这两个链接。

- **全库没有 `a { cursor: pointer }`**,只有 `.selbar a` 一处局部声明(`index.css:427`)。
- 浏览器**只给 `a[href]` 手型**,而本项目的链接一律是 `<a onClick>` 无 href
  (刻意的:渲染层不做页面跳转,点击走 IPC 或 `openExternal`)。
- 那为什么别处看着正常?**antd 把 `cursor: pointer` 按组件作用域注入**
  (`theme/util/genStyleUtils.js` 的 `getResetStyles` → `genLinkStyle`),
  所以落在 `.ant-list` / `.ant-tooltip` 里的 `<a>` 顺带拿到了手型。

逐一核过全部 15 处 `<a onClick>`,**实际受影响的只有安哥指出的这 2 处**:

| 位置 | 有手型 | 原因 |
|---|---|---|
| `Subscriptions.tsx:241` 策略行的 ⚙ | ❌ | 在我们自己的 `<div>` 里 |
| `Subscriptions.tsx:247` 打开检查日志 | ❌ | 同上 |
| 行内动作 / 待处理标题 / 检查记录 / 候选号「订阅」 | ✅ | 在 antd `List` 作用域内 |
| 文库批量栏(全选/清除/导出/同步) | ✅ | `.selbar a` 有局部声明 |
| 站点同步 Tooltip 里的仓库链接 | ✅ | 在 `.ant-tooltip` 作用域内 |

**所以真正的问题是:一个链接有没有手型,取决于它的祖先恰好是不是 antd 组件——这是偶然,不是设计。**
只补这两处等于把同一个坑留给下一个写在 antd 组件外面的链接。

**方案**:

- **在 `index.css` 加一条全局规则**,让"可点的 `<a>`"自己就有手型,不再依赖祖先是谁。
  同时删掉 `.selbar a` 里冗余的 `cursor: pointer`(它现在是全局兜住的,留着会让人以为局部必须声明)。
- **顺带核一遍其它可点元素**:凡是靠 `onClick` 而不是 `<button>` 实现的(卡片、分组头、表头排序等),
  确认都已有 `cursor: pointer`——上面查到的几处 `.ghead`/`.article-card`/`.lrow`/`.lh-sort` 都有,
  但**这次要把"检查清单"落成可回归的东西**,而不是又一次目视扫过。
- **不改成 `<button>`**:这些是"看着像链接、行为是动作"的元素,antd 的 List actions 也期望 `<a>`;
  为了语义纯度整体重构与本需求收益不成比例(真要做是独立的一次可访问性专项)。

**验收(草)**:

- [ ] 策略行的 ⚙ 与「打开检查日志」hover 时是手型。
- [ ] 修法是**全局规则**而不是给这两处各加一行 style
      ——下一个写在 antd 组件外的链接不该再踩一次。
- [ ] `.selbar a` 的冗余 `cursor` 已删,行为不变(文库批量栏仍是手型)。
- [ ] **e2e 断言 computed style**:至少覆盖「antd 作用域外的链接」这一类
      (`getComputedStyle(el).cursor === 'pointer'`)。目视验证会随改版失效,断言不会。
- [ ] 阅读器正文里的真链接(`.prose a`,有 href)行为不回归。

### R2 · GitHub 又报了一批安全告警(2026-07-28 安哥)

**核实结论(2026-07-28,`gh api .../dependabot/alerts`)**:**23 条 open,涉及 7 个包,全部有补丁**。

先说一个操作层的坑:**`npm audit` 在国内镜像下不可用**
(`registry.npmmirror.com` 返回 `[NOT_IMPLEMENTED] /-/npm/v1/security/*`),
所以本项目的安全事实来源是 **GitHub Dependabot**(或显式 `--registry=https://registry.npmjs.org` 跑 audit)。
别因为 `npm audit` 没报就以为干净。

| 包 | 条数 | 最高级别 | 补丁版本 | 作用域 | 够不够得着 |
|---|---|---|---|---|---|
| axios | 10 | medium | 1.18.0 | **运行时** | 选项解析的多项式耗时;**我们的 axios 选项是代码里的常量**,不由外部输入构造 |
| react-router | 5 | high | 见下 | **运行时** | 见下 |
| brace-expansion | 3 | high | 2.1.2 | 开发 | 只在构建/测试链路 |
| fast-uri | 2 | high | 3.1.4 | 开发 | 同上 |
| js-yaml / postcss / tar | 各 1 | high/medium | 4.3.0 / 8.5.18 / 7.5.18 | 开发 | 同上 |

**react-router 这 5 条要分开看**(当前 7.17.0):

- **4 条补丁是 `7.18.0`**——同大版本内的小版本升级,**照升**(开放重定向、反序列化注入、协议校验、DoS)。
- **剩下 1 条(RSC Mode CSRF Bypass)补丁是 `8.3.0`**,即**大版本升级**。
  但本项目**用不到那条代码路径**:渲染层是 Electron 里的 `HashRouter`(`main.tsx:13`),
  **没有服务端、没有 RSC、没有 server action**。为一条够不着的告警吃一次 major 升级,
  收益与风险不成比例。

**方案(倾向,安哥可推翻)**:

- **能靠小版本/补丁版升的全升**:`axios` 1.17→1.18、`react-router-dom` 7.17→7.18,
  开发依赖的那 5 个包靠更新其父级(vite / vitest / electron-builder)或 `npm update` 收敛。
- **RSC 那条不升 major,改为在 GitHub 上 dismiss 并写明理由**(「本项目不使用 RSC 模式」)。
  **dismiss 不是掩盖**:留下判断依据,比装作没看见或盲目 major 升级都诚实。
  ——若日后真引入 RSC/服务端渲染,这条要重新评估。
- **依赖升级必须真验**:v0.2.1 的教训是依赖升级的风险在打包与运行时,不在单测。
  升完要 `npm test` + `lint` + `tsc` + e2e + **真实启动打包后的 .app**(undici external 那条不变量)。

**验收(草)**:

- [ ] Dependabot open 告警从 23 降到 **仅剩那条 RSC(且已 dismiss 并写明理由)**,
      核实方式是重新 `gh api .../dependabot/alerts` 数一遍,**不靠「应该修好了」**。
- [ ] `axios` / `react-router-dom` 升级后功能不回归:下载单篇、按公众号抓取、订阅检查、页面路由跳转。
- [ ] 打包后的 .app 真实启动 + 跑一条 CLI(undici external 仍站得住)。
- [ ] 把「`npm audit` 在国内镜像下不可用」写进 AGENTS.md 的陷阱清单
      ——这条不写下来,下次还会有人拿 `npm audit` 的沉默当安全。

### R3 · README 重做:顺序乱、截图过时、说明落后于产品(2026-07-28 安哥)

**原始需求**:「项目状态」小节 v0.8.0 之后的顺序乱了;项目说明、截图也过时了,重新生成一份最新的 README。

**核实结论(2026-07-28)**:三处都属实,而且**顺序乱有个可复现的成因**,不修根因还会再乱。

| 问题 | 实况 |
|---|---|
| 顺序乱 | v0.1.0 → v0.8.0 **升序**,之后 v0.8.5 → v0.8.1 **降序**。成因:每次发版我都把新版块插在「上一个最新版块」之前,而那个锚点在 v0.8.0 之后——于是新版本一路往上堆,形成两段相反的序 |
| 截图过时 | 全部 5 张停在 **2026-06-09**(v0.2.0/v0.2.1 时期),此后 `src/renderer` 有 **50 次提交**;更要命的是图上方那句注释写着「后续版本 UI 一致」——**这句现在是假的** |
| 截图缺整块 | **订阅页(v0.3.0 起的主线之一)与阅读器根本没有截图**;文库卡片的类型标识/视频标识、设置页的更新检查与站点同步也都没入镜 |
| 说明落后 | 「这是什么」的 5 条里**没有订阅**这一整块能力,也没有站点同步、素材导出、更新检查 |
| CLI 清单缺项 | 子命令清单缺 `library export`/`rebuild`、`site sync`、`update --check`、`subscription digest`,以及 `crawl` 的日期范围与关键词筛选、`--no-video` |
| **一处事实错误** | 架构一节写「`src/renderer/` 缺失时即 CLI 模式」——**实际是 `electron/cli-dispatch.ts` 的 `CLI_COMMANDS` 白名单分流**(AGENTS.md 有专门的陷阱条目) |
| 重复 | 「项目状态」那 100 行完整版本史与 `ROADMAP.md` 的发布史**是两份同样的东西**——两处必漂,如今已漂 |

**关键判断:顺序乱不是手滑,是「同一份信息维护在两处」的必然结果。**
所以重做 README 的首要动作不是排序,而是**让 README 不再承载完整版本史**:
它只留「最新版本亮点 + 一句指向 ROADMAP」,历史归 ROADMAP 一处维护。
只把顺序理顺而保留那 100 行,下次发版照样会再乱一次。

**方案**:

- **重写 README**,回到它该回答的三个问题:**这是什么 / 能干什么 / 怎么用**。
  - 「这是什么」补齐订阅、站点同步、素材导出、更新检查;
  - CLI 清单补全到当前命令集(以 `wx-kit-skill` 的速查表为准,别另写一份会漂的);
  - 修掉模式分流那处事实错误;
  - **「项目状态」瘦身**:只留当前版本与一句「完整发布史见 ROADMAP」。
- **重拍全部截图**,并补上缺的两屏(订阅、阅读器):
  - **必须用真实数据态**(隔离 userData + 真实文库或借真实登录态驱动到有内容的状态)——
    空库截图看不出产品在干什么;
  - 拍完把图上那句「后续版本 UI 一致」换成**具体版本号**,别再写一个会过期的承诺。
- **发版规约补一条**:README 的截图在 UI 有明显变化的版本要重拍。
  现状是发版只刷版本号相关处(规约⑤),截图不在清单里——这也是它能停在两个月前的原因。

**验收(草)**:

- [ ] README 通读一遍,**没有与当前实现矛盾的陈述**(尤其模式分流那处)。
- [ ] 「项目状态」不再重复 ROADMAP 的发布史;版本顺序问题**从结构上消失**(没有需要排序的长列表)。
- [ ] 截图为当前版本、真实数据态,含**订阅页与阅读器**;图注写明版本号。
- [ ] CLI 子命令清单与 `wx-kit --help` 实际输出一致(逐条对过,不是凭印象)。
- [ ] 发版规约(AGENTS.md)补上「UI 有明显变化时重拍截图」。

### R4 · 订阅 pending 里的违规文章:下不了又看不出为什么(2026-07-30 安哥)

**原始现象**:订阅检查会把违规文章也列进 pending,但**不标明违规**;
用户点下载**下不下来**,**一直挂在待处理里**,只能手动选「忽略」才知道它是坏的。

**核实结论(2026-07-30 读代码)**:现象属实,而且**M40 的"自动移除 unavailable"逻辑没生效**——
否则那篇不会"一直"挂着。根因有两层,都得说清楚:

1. **`describeUnavailable` 只认三种错误页文案**(`download-article.ts:30-35`):
   「此内容发送失败无法查看」/「已被发布者删除」/「内容违规|涉嫌违规」。
   **实际违规页的文案如果不在其中,就走兜底,被当成普通失败(`unavailable: false`)**
   ——于是 M40 的"unavailable 从 pending 移除"那条路径根本没触发,文章卡在 pending 里,
   与"普通网络故障"长得一模一样。这正是安哥看到的现象:**下不了、看不出为什么、只能靠忽略**。
2. **即便识别准了,M40 的处理是"静默从 pending 移除"**——这也不对:
   用户会困惑「明明 N 篇,怎么只剩 M 篇」,与 v0.8.3 定下的
   **「做不到就承认,转而消灭误解而非消灭失败」**相悖。
   unavailable 该被**看见**而不是**消失**。

**两层共同指向同一个修法方向**:**让 pending 条目带「上次下载尝试的结论」,UI 按结论显示**。

- **数据**:在 `SubscribedAccount` 上加一个旁路记录 `refAttempts?: Record<refId, { ok; unavailable?; error?; at }>`,
  **不污染 `ArticleRef`**(它是列表接口的纯数据,不该混入运行期下载状态)。
  老数据没这个字段 = 「没试过」,零迁移。
- **UI**:pending 条目按 `refAttempts[refId]` 分四态显示:
  - 没试过 → 现状(勾选 + 标题)。
  - 试过且成功 → 不该出现(成功的已从 pending 移除);出现说明状态不一致,按"已下载"标出。
  - 试过且 `unavailable: true` → **明确标「读者不可见(审核未通过/已删除/违规),重试无用」**,并给「忽略」一个高亮快捷入口。
  - 试过且失败(非 unavailable)→ 标「上次下载失败:〈原因〉,可重试」,与上面那类**视觉上分开**
    ——一类是"别试了",一类是"可以再试"。
- **M40 的"自动移除 unavailable"改为"留在 pending 并写 refAttempts"**:
  让用户看见,而不是悄悄消失。
- **顺带扩 `describeUnavailable` 的识别**:实现时若能拿到真实样本(让安哥提供一个当前卡着的 URL),
  先看错误页实际文案,补进识别条件——**但识别准不准不再决定用户看不看得出分类**
  (就算走兜底,用户也看得见"失败 + 笼统原因",不会以为工具坏了)。

**⚠️ 一条与 v0.8.3 教训的对齐**:那条教训原话是「做不到就承认,转而消灭误解而非消灭失败」。
M40 把 unavailable 从 pending 拿掉是"消灭失败";R4 改回"消灭误解"——**让用户看见分类,
哪怕那意味着 pending 里会有几条永远清不掉的"不可见"**。能一键忽略全部不可见的,是配套动作。

**验收(草)**:

- [ ] 订阅 pending 里,试过下载且 unavailable 的条目**明确标出**「读者不可见」,
      与"网络失败可重试"视觉上分开;不会"挂着看不出为什么"。
- [ ] unavailable 的条目**不再静默从 pending 移除**;保留并标状态,提供「忽略」入口。
- [ ] 提供「忽略所有不可见的」批量动作(unavailable 的通常一次一批,逐个忽略太累)。
- [ ] 扩 `describeUnavailable` 的识别(若有真实样本);**即使识别不准,UI 也能给出笼统的失败原因**,
      不再让用户对着无标识的条目瞎猜。
- [ ] 老的 subscriptions.json(无 `refAttempts`)正常加载,所有 pending 显示为"没试过"。
- [ ] 单测覆盖:unavailable 写进 refAttempts、UI 按 refAttempts 分态渲染、批量忽略。
- [ ] 真机验证:用一个真实的违规 URL(或人工制造一个 unavailable)走完整路径。

### R5 · 公众号重新登录与彻底退出登录(2026-08-02 安哥)

**原始需求**:需要提供公众号重新登录、退出登录;退出登录要清理所有与登录状态相关的
partition Cookie 等数据。

**核实结论(2026-08-02,当前 HEAD)**:当前版本没有重新登录/退出登录入口,而且登录态实际存了两份:

1. Electron `userData` 下的 `mp-session.json`:保存 `token`、Cookie 副本和扫码时间,
   后续公众号搜索、抓取、订阅检查直接读取它。
2. 登录窗口使用的持久分区 `persist:mpweixin`:微信后台页面自身的 Cookie、Local Storage、
   IndexedDB、Service Worker、Cache Storage 等站点数据会跨窗口、跨应用重启保留。

现有 `clearSession()` **只删除 `mp-session.json`**。这不等于退出登录:
旧分区仍可能让微信后台自动进入原账号,导致用户点「重新登录」却没有机会扫码换号。
反过来只清分区也不够,因为应用仍可能拿旧的 `mp-session.json` 请求公众号接口。
2026-08-02 曾有一版临时实现只清 Cookie,现已回退;本需求按更完整的边界重新收录,
**不能把那版提交直接恢复后就算完成**。

**方案**:

- 设置页新增「公众号账号」区,显示「已登录(扫码时间) / 未登录」,
  已登录时提供「重新登录」和「退出登录」。当前会话没有可靠的公众号名称,
  **不伪造“当前登录账号”展示**。
- 主进程提供唯一的 `clearMpAuthState` 能力,重新登录与退出登录都调用它,避免两条路径清理标准漂移:
  1. 删除应用持有的 `mp-session.json`;
  2. 清空专用于微信后台的整个 `persist:mpweixin` 分区存储,而不是只删当前能看见的几枚 Cookie;
     至少覆盖 Electron `clearStorageData()` 管理的 Cookie、File System、IndexedDB、Local Storage、
     WebSQL、Service Worker、Cache Storage 等全部站点存储,并清理该分区的 HTTP 缓存和认证缓存;
  3. 某项清理失败时返回明确失败,**不得显示「已退出」后仍残留可复用的旧登录态**。
- 「重新登录」的语义是:**先彻底退出旧会话,再打开扫码窗口**。
  如果用户取消扫码,应用保持未登录并明确提示,不能偷偷回退到旧账号。
- 「退出登录」成功后立即刷新界面状态;后续搜索、抓取、订阅检查都按未登录处理,
  应用重启后也不能恢复旧账号。
- 公众号登录分区名只定义一处,登录窗口与清理逻辑共用,防止以后改了 partition 名却漏改清理路径。
- 清理范围只限**应用管理的有效登录态**。文库、下载历史、订阅、设置和已下载文件都必须保留。
  用户通过 `session export` 手动导出到外部路径的备份不属于应用当前登录态,
  应用既不知道所有副本位置也不能越权删除;退出登录后它不能继续生效,除非用户再次主动导入。

**验收(草)**:

- [ ] 设置页能看见公众号登录状态;已登录时有「重新登录」与「退出登录」入口。
- [ ] 登录账号 A 后点「重新登录」,必须出现扫码流程而不是自动进入 A;
      扫码账号 B 成功后,后续公众号请求使用 B 的新 token/Cookie。
- [ ] 重新登录中途取消后保持未登录,界面与后续操作都不再把 A 当成有效会话。
